# Оценка качества: TEST-04 — Регистры, обновляемые при работе с задачами
**Сервер:** rlm-tools-bsl (v1.17.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Все 4 подвопроса закрыты данными из MCP: найдены **6 регистров** (2 накопления + 4 сведений), прочитан реальный код процедур-писателей, прослежена логика пересчёта ресурсов при смене статуса, найдены обслуживающие регламентные задания. Ответ опирается на код и метаданные, без существенного «додумывания».

## Что сервер дал хорошо
- **Профильные «регистровые» инструменты** — именно под этот вопрос: `find_register_writers` (#9: какие документы пишут в каждый регистр), `find_register_movements`, `find_event_subscriptions` (#7: 70+ подписок), `find_scheduled_jobs` (#33). Прямой ответ «кто пишет», без обходных путей.
- **Структура 4 регистров одним вызовом** (#8): измерения + ресурсы + атрибуты КоличествоЗадач, КоличествоДействийЗадач, ДействияЗадач, ВсеИсполнителиДействийЗадач.
- **6 регистров покрыты**: РН `КоличествоЗадач`, `КоличествоДействийЗадач`; РС `ДействияЗадач` (40 ресурсов), `ВсеИсполнителиДействийЗадач`, `ЗадачиПоАвторам` (27 ресурсов), `ИсторияЗадач`.
- **Реальный код-писатель**: `ОбработкаПроведения`/`ПриЗаписи` обоих документов (Задача, ДействиеЗадачи), `RecordSetModule.ОбновитьДанныеЗадачи` (маппинг ВидСостоянияЗадачи → ресурсы = 1/0), `ЗаполнитьНаборПоДействию` (записи по замещающим).
- **Логика смены статуса** (#18, #30): `ОбработатьИзменениеСостоянияЗадачи`, `ИсторияЗадач.Добавить('Закрыта'/'ЗакрытаПодзадача')`.
- **Регламентные задания** (#34): `ПометкаЗадачПросроченными` (use=True), `ОбслуживаниеИтоговЗадач` (пересчёт итогов РН).

## Что сервер НЕ дал
- Принципиальных пробелов нет — все 4 подвопроса закрыты прямыми данными, включая код и регламентные задания.

## Паттерны поведения агента
- Сессионный цикл с рецептом «движения»: `rlm_help topic=движения` → `find_register_movements`/`find_register_writers`/`find_event_subscriptions` → `read_procedure`.
- **Адаптация к типу объекта**: `find_register_movements('ЗадачаИсполнителя')` вернул пусто (Task не проводится) → retry на `find_event_subscriptions` + `find_register_writers` по документам Задача/ДействиеЗадачи. Корректная реакция на специфику конфигурации.
- Второй retry (#32→33): узкий `find_scheduled_jobs` дал пусто → повтор без фильтра, нашёл задания.
- Расход рос плавно: **ни одного скачка >20%** (максимум — #4 rlm_start ≈9.6%). Нет ⚠️.

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| `find_register_movements` не применим к Task | #6 пустой результат (ожидаемо: Task не проводится) → 1 retry на корректную стратегию |
| `find_scheduled_jobs` чувствителен к фильтру | #32 узкий запрос дал 0 → 1 retry без фильтра |

## Вывод
rlm-tools-bsl v1.17.0 закрыл TEST-04 полностью при ≈185K токенов. Этот вопрос играет на сильной стороне сервера — **наличие специализированных инструментов под регистры и поток данных** (`find_register_writers`, `find_register_movements`, `find_event_subscriptions`, `find_scheduled_jobs`), которые дают прямой ответ «кто и что пишет» без чтения сырого XML. Структуры регистров получены одним вызовом, код-писатели прочитаны напрямую, цепочка смены статуса прослежена. Минорные шероховатости — два быстрых retry на специфику (Task не Document; фильтр jobs). Профиль расхода ровный, без ⚠️.
