# Оценка качества: TEST-10 — Сквозной сценарий (письмо → резолюция → задача → ответ)

**Сервер:** rlm-tools-bsl (v1.17.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Все 5 шагов сквозного сценария покрыты данными из кода и метаданных: структуры `Document.ВходящееПисьмо` (23 рекв.+4 ТЧ) и `Document.ИсходящееПисьмо` (27 рекв.+4 ТЧ, ключевой `ПисьмоОснование`→DocumentRef.ВходящееПисьмо), **обе ветки шага 2** — `BusinessProcess.Рассмотрение` (структура + Резолюция/ШаблоныРассмотрения) и модуль `РаботаСРезолюциями` (`ПолучитьРезолюции`…), `Document.Задача` + `BusinessProcess.Исполнение` → `Task.ЗадачаИсполнителя`, выполнение через `ВыполнениеЗадачСервер.ВыполнитьЗадачу`, формирование ответа (`ОбработкаЗаполнения`→`ЗаполнитьСтруктуруРеквизитовПоПисьму`, ТипОтвета=ОтветНаПисьмо), 18 регистров сведений с измерениями/ресурсами, 5 активных регл. заданий, ввод на основании. 44 вызова, ≈204K токенов, без ⚠️.

> **Сверка с исходником (оркестратор):** ключевые объекты подтверждены прямым чтением — `BusinessProcesses/Рассмотрение.xml` и `BusinessProcesses/Исполнение.xml` существуют (rlm корректно разобрал оба процесса), `Documents/Задача.xml` существует. **Тонкость шага 2:** rlm подал «резолюцию» как текстовый реквизит БП Рассмотрение + общий модуль `РаботаСРезолюциями`, но **не назвал отдельный объект `Catalog.Резолюции`** (он реально существует — `Catalogs\Резолюции.xml`). То есть rlm точно описал *процесс* вынесения резолюции, но не *объект-справочник*, в котором она хранится. bsl — наоборот: назвал `Catalog.Резолюции`, но пропустил БП Рассмотрение. Шаг 2 у обоих закрыт зеркально-частично; остальные 4 шага у rlm полны.

## Что сервер дал хорошо
- **Структуры обоих писем** (#8, #9, `parse_object_xml`): ВходящееПисьмо (23 рекв. + 4 ТЧ, Posting=Deny), ИсходящееПисьмо (27 рекв. + 4 ТЧ) с **ключевой связью** `ПисьмоОснование` (DocumentRef.ВходящееПисьмо|ИсходящееПисьмо) — прямая нить «ответ на письмо».
- **Шаг 2 как процесс** (#15, #17, #31): `BusinessProcess.Рассмотрение` (Резолюция, ВариантОбработкиРезолюции, ОбрабатывающийРезолюцию, ШаблоныРассмотрения) + модуль `РаботаСРезолюциями` (ПолучитьРезолюции, ЭтоАвторРезолюции, ПроверитьДоступНаПодписание) + форма параметров резолюции.
- **Шаг 3 структурно** (#12, #14): `Document.Задача` (30 рекв.+2 ТЧ Приложения/Участники, проводимый) и `BusinessProcess.Исполнение` (Исполнители, Контролер, Шаблон, ВариантИсполнения→ВариантыМаршрутизацииЗадач).
- **Запуск процессов по действию** (#30, #32): `РаботаСПроцессамиПоДействиям.СоздатьПроцессыПоДействию` → запись в РС `ПроцессыДействий`, создание процессов Рассмотрения/Исполнения/Ознакомления/Подписания/Регистрации/Согласования по типу действия.
- **Системный обзор регистров** (#22, #23, #33–36): `tree InformationRegisters` + `parse_object_xml` с **измерениями и ресурсами** — ДанныеБизнесПроцессов, ДействияЗадач (40 ресурсов), ВсеИсполнителиДействийЗадач, ИсторияЗадач, ЗадачиПоАвторам, КоличествоПисемВПапках, ВложенныеПисьма, ИсторияСостоянийДокументов, НаличиеФайлов, ВерсииОбъектов.
- **Реальный код шагов** (#26–29, #37, #40, #43): ПередЗаписью/ПриЗаписи ВходящегоПисьма (КоличествоПисемВПапках, СведенияОбАдресатах, РаботаСРабочимиГруппами), ВыполнитьЗадачу (права, очередь заданий, события), ОбработкаЗаполнения Задачи (создание из письма → ТЧ Приложения), ЗаписатьВходящееПисьмо (транзакция, СоздатьДокумент).
- **Регл. задания** (#41): 5 активных (ОтправкаПисем, ОтправкаПисемПоВнутреннейМаршрутизации, ОбслуживаниеИтоговЗадач, ПометкаЗадачПросроченными, ПовторениеБизнесПроцессов).
- **Ввод на основании** (#42): ВходящееПисьмо → Задача; Задача ← письма/задачи/действия/проекты.

## Что сервер НЕ дал
- **Объект `Catalog.Резолюции`** — не назван явно (резолюция подана как реквизит БП + модуль). Объект существует и хранит резолюции — пробел в идентификации объекта шага 2.
- **Кастомизация Тест на задачах** — тст_-регистры (тст_СрокиИсполненияЗадач, тст_СогласованиеЗаявокСБ, тст_ИзмененияОценкиРискаКонтрагентов), которые пишутся при ПриЗаписи/ПриВыполнении ЗадачиИсполнителя, rlm не вскрыл (это нашёл bsl чтением ObjectModule).
- **Код связки «резолюция → создание задачи»** — выведен логически из структур/подписок, отдельная процедура не прочитана (самооценка агента).
- **Механизм прикрепления файла-ответа** — через ТЧ Приложения и подписки РаботаСФайлами, без чтения конкретной процедуры.

## Паттерны поведения агента
- Сессионный цикл, богатый профиль структурных инструментов: `search_objects` → `parse_object_xml` → `find_event_subscriptions` → `tree`/`find_by_type` (регистры) → `read_procedure` → `find_scheduled_jobs` → `find_based_on_documents`.
- 2 retry (#7→8 формат пути; #16→17 ошибка итерации params) — оба восстановлены. 3 шумных вызова (неверный путь, пустой git_search, glob по CF не работает).
- Расход **ровный, без ⚠️** (максимум — #11 подписки ≈13.1%, #35 регистры+подписки ≈7.5%). 41 из 44 вызовов полезны.
- **Цена по времени**: ~22 мин — самый долгий прогон по wall-clock (44 последовательных rlm_execute), хотя по токенам экономно.

## Вывод
rlm-tools-bsl v1.17.0 закрыл TEST-10 полностью при ≈204K токенов, без ⚠️ — **самое широкое и системное структурное покрытие** сквозного сценария: обе ветки БП (Рассмотрение и Исполнение), структуры писем и Задачи, 18 регистров с измерениями/ресурсами, регл. задания, ввод на основании, реальный код ключевых обработчиков. Сильная сторона — `parse_object_xml`/`tree`/`find_event_subscriptions` дают полную карту объектов и регистров. Пробел шага 2 — не назван объект `Catalog.Резолюции` (резолюция подана как процесс+модуль), и не вскрыта кастомизация Тест на задачах (тст_-регистры), которую нашёл bsl. По цене токенов почти паритет с bsl (1.07×), но по wall-clock дороже (22 мин против 6). Для запроса «опиши сквозной сценарий с объектами/процессами/регистрами/кодом» rlm даёт наиболее полную *структурную* модель; для глубины конкретного кода и кастомизации полезен взгляд bsl.
