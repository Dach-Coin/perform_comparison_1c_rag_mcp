# Оценка качества: TEST-01 — Жизненный цикл входящего документа
**Сервер:** rlm-tools-bsl (v1.17.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Все 5 подвопросов закрыты данными из MCP. Реквизиты, обработчики записи, бизнес-процессы, регистры и логика регистрации получены из индекса и кода, без «додумывания» по существу.

## Что сервер дал хорошо
- **Структура документа мгновенно из индекса**: 23 реквизита с типами + 4 табличные части + 4 формы + 3 перечисления (1 вызов, #11).
- **Полный текст обработчиков** `ПередЗаписью` (стр. 5–47) и `ПриЗаписи` (49–107) с разбором вызовов: `ВстроеннаяПочтаСервер.ПрименитьПравила`, `РегистрыСведений.КоличествоПисемВПапках.ОчиститьЗаписиПоПапке`, `РаботаСРабочимиГруппами.*`.
- **86 глобальных подписок на события** — читаемый список с именами обработчиков и модулей (кириллица не повреждена).
- **Граф вызовов из коробки**: `rlm_start effort=high` поднял индекс на 88 555 методов и 459 440 рёбер вызовов; `find_code_usages` дал 175 использований `Document.ВходящееПисьмо`.
- **XML-подтверждение 7 бизнес-процессов** (Исполнение, Рассмотрение, Согласование, Ознакомление, Подписание, Утверждение, КомплексныйПроцесс) через `git_search` по метаданным.
- **Структуры регистров** (КоличествоПисемВПапках, СведенияОбАдресатах, ПротоколРаботыСотрудников, ЗначенияУсловийПриОбработкеПисем) с измерениями и ресурсами.

## Что сервер НЕ дал
- **Собственная нумерация ВходящегоПисьма** — отсутствует by design (это почтовый, а не деловой документ); сервер косвенно это подтвердил (`ПолучитьПараметрыНумерации` работает с `ДокументыПредприятия`). Не дефект сервера, а свойство конфигурации.
- **Код запуска БП из UI** — инициируется кнопками форм, а не из ObjectModule; метаданные подтвердили допустимые предметы, но самого «триггера» в коде объекта нет.
- **Прямые писатели регистра** `КоличествоПисокВПапках` — `find_register_writers` не нашёл прямой записи, т.к. обновление идёт через метод менеджера (`ОчиститьЗаписиПоПапке`), а не прямой записью; ограничение хелпера на косвенные записи.

## Паттерны поведения агента
- Классический сессионный цикл: `rlm_help` (изучение рецептов) → `rlm_projects list` → `rlm_start effort=high` → серия `rlm_execute` → `rlm_end`.
- Восстановился после транзиентной недоступности classifier (2 retry, ~5 сек паузы) без потери хода.
- Чередовал семантический поиск (search_objects, find_code_usages) с прямым чтением кода и `git_search` по XML для верификации — эффективная стратегия перекрёстной проверки.
- Расход контекста рос плавно и контролируемо: ни один вызов не дал скачка >20% от итога (максимум — #27 на ~11%).

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Транзиентная доступность classifier | 2 ошибки подряд на #7→8, потребовался retry |
| Хрупкость ключей в get_object_full_structure | KeyError `attr_name` на #10, исправлено сменой ключей |
| find_register_writers не видит косвенные записи | Записи через метод менеджера не распознаны как «писатели регистра» |

## Вывод
rlm-tools-bsl v1.17.0 закрыл TEST-01 полностью при минимальном и контролируемом расходе контекста (≈163K токенов MCP-ответов). Сильные стороны — мгновенная структура объектов из индекса, полный код обработчиков, читаемые подписки и граф вызовов. Подходит для глубокого анализа кода/структуры и трассировки вызовов; слабые места — транзиентная доступность classifier и слепое пятно к косвенным записям в регистры.
