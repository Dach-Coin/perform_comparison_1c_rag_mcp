# Оценка качества: TEST-03 — Структура справочника Сотрудники
**Сервер:** rlm-tools-bsl (v1.17.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Все 5 подвопросов закрыты структурными данными из индекса: 9 реквизитов с типами + 2 ТЧ (одним вызовом), owner-связь с ФизическимиЛицами (из XML), типы ссылок на Должности/СтруктураПредприятия, **актуальный механизм замещения** (`ЗамещающиеИПомощники`) с кодом и регистрами, профильные регистры. Реконструкция опирается на код и метаданные, без существенного «додумывания».

## Что сервер дал хорошо
- **Структура объекта одним вызовом** (#7): 9 реквизитов с типами + 2 ТЧ (ДополнительныеРеквизиты, КонтактнаяИнформация со всеми колонками) + 5 форм.
- **Owner-связь из метаданных** (#10, `parse_object_xml`): `ref_kind='owner'` → Сотрудники подчинены ФизическимЛицам. Типы реквизитов подтвердили связи с Должности/СтруктураПредприятия; найдена обратная ссылка СтруктураПредприятия.Руководитель→Сотрудники.
- **АКТУАЛЬНЫЙ механизм замещения** (#15–17, #27–28): справочник `ЗамещающиеИПомощники` (9 реквизитов + ТЧ ВопросыЗамещения), CommonModule `ЗамещающиеИПомощники` (14 экспортов), код `АктуальныеЗамещенияСотрудников` (запрос с `Действует=Истина`), регистры `ИсполнителиРолей`/`ИсполнителиРолейИДелегаты` (измерение НастройкаДелегирования→ЗамещающиеИПомощники), регламентное задание `ОбработкаСроковЗамещающихИПомощников` (use=True).
- **Регистры через структуру + git_search** (#11, #13, #32–34): ОсновныеСотрудники, СотрудникиПользователей, РабочееВремяСотрудников (накопление, 4 ресурса длительности), КоличествоДействийЗадач, ДанныеSAPСотрудники, ПротоколРаботыСотрудников и др.
- **Поведенческий код** (#23–26): `ЗаполнитьНаименование` (`Наименование = Строка(Владелец)`), `ЗаполнитьПредставления`, `УстановкаПараметровСеанса` (ОсновнойСотрудник, РолиТекущегоПользователя).
- **Подписки на события** (#20): 92 подписки, ключевые `Документооборот*ПравообразующихОбъектов` → пересчёт прав при записи Сотрудника/Замещения.

## Что сервер НЕ дал
- **Полный список регистров сведений одним вызовом** — `find_by_type('InformationRegisters')` ограничен 20 записями (#14, #31); пробел закрыт через `git_search` (#32).
- Принципиальных пробелов нет — все 5 подвопросов закрыты прямыми данными.

## Паттерны поведения агента
- Сессионный цикл: `rlm_help` ×2 → `rlm_projects list` → `rlm_start effort=high` → 30× `rlm_execute` → `rlm_end`.
- Два retry: #6 (ключи структуры attr_name→name, по HINT) и #9 (путь `.mdo`→директория, по HINT) — оба восстановлены сразу. Та же хрупкость ключей, что в TEST-01/02.
- Грамотно комбинировал `get_object_full_structure` / `find_enum_values` / `parse_object_xml` (метаданные) с `read_procedure` (поведение) и `git_search` (полнота списка регистров).
- Расход рос плавно: **ни одного скачка >20%** (максимум — #4 rlm_start ≈13.5%). Нет ⚠️.

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Хрупкость ключей/путей в структурных вызовах | #6 (KeyError attr_name), #9 (FileNotFound .mdo) — по 1 retry, восстановлено по HINT |
| `find_by_type` ограничен 20 результатами | Полный список регистров сведений потребовал обхода через `git_search` |

## Вывод
rlm-tools-bsl v1.17.0 закрыл TEST-03 полностью при ≈118K токенов — и, что важнее, **корректно определил актуальный механизм замещения** (`ЗамещающиеИПомощники` + регистры делегирования + регламентное задание), не сведя его к устаревшей ТЧ. Структура объекта получена одним вызовом, owner-связь — из метаданных, регистры — комбинацией структуры и git_search. Слабости минорные: хрупкость ключей структурных вызовов (2 быстрых retry) и лимит `find_by_type` в 20 записей. Профиль расхода ровный, без ⚠️-скачков. Сильный результат для анализа структуры справочника и его окружения.
