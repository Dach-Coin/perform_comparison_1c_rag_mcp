## Что сервер дал хорошо

1. **БП Подписание** — 20 атрибутов (СпособПодписания, РезультатПодписания, ПорядокВыполненияУчастниками, КоличествоИтераций), ТЧ Участники с 13 атрибутами (Подписывающий, ТочкаМаршрута, Условие, СрокИсполнения), 3 формы. Полная структура.
2. **РС ЭлектронныеПодписи** — измерения ПодписанныйОбъект + ПорядковыйНомер, 17 ресурсов включая Подпись, Сертификат, ТипПодписи, ДатаПодписи, ПодписьВерна, СертификатДействителен. Основное хранилище ЭП раскрыто полностью.
3. **Справочник СертификатыКлючейЭлектроннойПодписиИШифрования** — 26 атрибутов, ключевые флаги Подписание/Шифрование/Отозван, связи с Пользователем и ФизическимЛицом.
4. **Экосистема модулей** — найдены 14+ общих модулей: РаботаСЭП (центральный), МаршрутыПодписанияБЭД (4 модуля), РаботаСВнешнимПодписанием (3 модуля), СервисКриптографии/Клиент, ЭлектроннаяПодписьСлужебныйКлиент.
5. **Ключевые функции кода** — ЗаписатьЭПФайлу, Подписать (CMS/GOST3410), ДобавитьПодписьКФайлу, ЗаполнитьИтоговыйРезультатПодписания, РезультатПодписанияДокумента ("Подписан"/"НеПодписан"/"Аннулирован").
6. **Внешнее подписание** — обнаружен документ СведенияОВнешнемПодписании (15 атрибутов) и модули РаботаСВнешнимПодписанием для КЭП-сервисов.

## Что сервер НЕ дал

1. **Тела процедур** — только сигнатуры и описания, невозможно увидеть реализацию ЗаполнитьИтоговыйРезультатПодписания или триггер смены статуса.
2. **Значения перечислений** — РезультатыПодписания, СпособПодписания, ВариантыПодписания — только имена объектов.
3. **Объектный модуль БП Подписание** — list_modules не поддерживается, агент компенсировал через search_code.
4. **Конкретный маршрут подписания** — как именно CMS vs GOST3410 выбирается в маршруте (атрибут ВидПодписи найден, но его тип/значения нет).

## Паттерны поведения агента

- **Стратегия:** параллельное исследование метаданных + код. Начал с search_metadata_by_description для обзора, затем drill-down по конкретным объектам, затем search_code по 4 направлениям (запуск, подписание, статус, модуль РаботаСЭП).
- **2 retry:** (a) "ЭлектронПодпис" не нашлось → "Электронны" starts_with — логичный fallback; (b) list_tabulars не поддерживается → list_tabular_attributes напрямую.
- **Дублирующий вызов** — call #24 дублирует #20 (РаботаСВнешним starts_with). Незначительная потеря.
- **Хорошее покрытие** — 34 вызова дали полную картину от бизнес-процесса до криптографии и внешнего подписания.

## Выявленные проблемы RAG
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Нет значений перечислений | РезультатыПодписания, СпособПодписания — имена есть, значений нет |
| list_tabulars / list_modules не поддерживаются | 2 ошибки, потеря 2 вызовов |
| Неоднозначность имён | МаршрутыПодписания (Подсистемы vs Справочники) — требует полного пути |
| Нет тел процедур | Конкретный алгоритм смены статуса документа восстановлен только по сигнатурам |
| Паттерн поиска чувствителен к форме | "ЭлектронПодпис" = 0 результатов, "Электронны" = 15 результатов |

## Вывод

Сервер показал отличный результат на сложной теме, охватывающей бизнес-процесс, криптографию, хранение подписей и интеграцию с внешними сервисами. Три инструмента (search_metadata, search_metadata_by_description, search_code) в комбинации дают достаточно информации для полного ответа. Сервер подходит для анализа сложных подсистем с множеством связанных объектов. Основная проблема — невозможность прочитать тело процедуры для понимания конкретной логики.
