## Что сервер дал хорошо

1. **Полный список реквизитов** Сотрудников (11 полей) через `list_attributes` — точный, структурированный ответ за один вызов.
2. **Связанные справочники** — реквизиты ФизическихЛиц (10), Должностей (2), СтруктурыПредприятия (7), ЗамещающихИПомощников (11) получены отдельными точечными запросами.
3. **Семантический поиск** (`search_metadata_by_description`) — нашёл все ключевые объекты с высокой точностью: Сотрудники (score 1.0), ФизическиеЛица, Должности, ЗамещающиеИПомощники в топе результатов.
4. **Регистры** — через `list_objects_by_name` с `match: "contains"` найдены все 13 регистров сведений, содержащих "Сотрудник" в имени. Структуры (измерения, ресурсы) получены для каждого.
5. **API-функции замещения** — `search_code` нашёл все ключевые процедуры: АктуальныеЗамещения, ОбновитьДанныеЗадачПоЗамещению, СотрудникиВключаяЗамещения, ЗаписьЗамещения и др.
6. **API-функции связей** — ФизЛицоСотрудника, ДолжностьСотрудника, ПодразделениеСотрудника получены из `search_code` с точными возвращаемыми типами.

## Что сервер НЕ дал

1. **Табличные части** — операция `list_tabulars` не поддерживается. Агент не смог подтвердить наличие/отсутствие ТЧ напрямую (определил косвенно — их нет).
2. **Типы реквизитов** — `list_attributes` возвращает только имена полей без типов. Типы определялись косвенно через API-функции (ФизЛицоСотрудника → СправочникСсылка.ФизическиеЛица).
3. **Список модулей** — `list_modules` не поддерживается. Агент не мог целенаправленно получить МодульОбъекта/МодульМенеджера.
4. **Тело кода** — `get_module_text` не поддерживается. Только сигнатуры и описания из `search_code`.
5. **Значения перечисления** ВидыЗамещения (Замещающий/Помощник) — определены косвенно из контекста кода, не напрямую.

## Паттерны поведения агента

- **Стратегия:** поэтапная — сначала `list_attributes` для структуры, затем `search_metadata_by_description` для семантического обзора, затем точечные `list_dimensions`/`list_resources` для регистров, в конце `search_code` для API.
- **Retry: 0** — агент не делал повторных попыток, грамотно адаптируя запросы при ошибках неподдерживаемых операций.
- **Шумные вызовы (6):** 4 из-за неподдерживаемых операций (list_tabulars, resolve_type, list_modules ×2) + 1 пустой ответ (list_resources) + 1 низкая релевантность.
- **Эффективность:** агент провёл 29 вызовов, но 23 полезных — каждый добавлял новые данные. Это больше, чем у других серверов в предыдущих тестах, но обусловлено точечным стилем API (одна операция = одна сущность).

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Отсутствие типов в list_attributes | Агент вынужден выводить типы косвенно через API-функции и семантический поиск |
| Неподдерживаемые операции (list_tabulars, list_modules, resolve_type, get_module_text) | 4 из 6 шумных вызовов — агент пробовал эти операции, получал ошибки |
| Большие ответы search_metadata_by_description | 67K и 74K символов — значительный расход контекста, при том что полезны лишь топ-10–15 результатов |

## Вывод

Сервер `1c-metacode-test-do3` **отлично справился** с задачей анализа структуры справочника. Его сильная сторона — точечные template-запросы `list_attributes`, `list_dimensions`, `list_resources`, которые дают компактные и точные ответы. `search_code` эффективно находит API-функции с описаниями. Слабые стороны: отсутствие типов в атрибутах, неподдерживаемые операции (tabulars, modules, get_module_text) и раздутые ответы семантического поиска. Для задач типа "покажи структуру объекта и связи" — один из лучших серверов.
