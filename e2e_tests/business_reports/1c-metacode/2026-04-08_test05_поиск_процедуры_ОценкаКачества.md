## Что сервер дал хорошо

1. **Целевая процедура найдена с первого вызова** — `search_code` сразу нашёл `ОпределитьФактическихИсполнителей` в `ОбщиеМодули.РаботаСЗадачами` (score 0.44) и несколько связанных функций.
2. **Полная сигнатура** — возвращаемая структура с 5 полями (ДействияБезФактИсполнителя, ДействияБезКомуАдресовано, ФактическиеИсполнителиПолные, ФактическиеИсполнителиПоДействиям, ОснованияФактИсполнителейПоДействиям) — полностью описывает контракт функции.
3. **Ядро замещений** — `ПодходящиеЗамещения` в `ОбщиеМодули.ЗамещающиеИПомощники` найдена через `search_code` с фильтрацией по owner, что дало точечный результат (8 процедур модуля).
4. **Полная цепочка вызовов** — восстановлена от UI (ВзятьВРаботуСВыборомИсполнителя, клиент) → серверный вызов (ВзятьВРаботу) → ОпределитьФактическихИсполнителей → ПодходящиеЗамещения. Плюс ветка записи: ПриЗаписиДействия → ЗаписатьДоступЗамещающихПоДействиюЗадачи.
5. **Справочник ЗамещающиеИПомощники** — структура (11 атрибутов) получена через `list_attributes`.
6. **Роли** — найден справочник ПолныеРоли и функция НайтиПоРолиИсполнителя (score 0.89) — подтверждает работу с ролями исполнителей.

## Что сервер НЕ дал

1. **Тело функции** — `get_module_text` не поддерживается. Алгоритм работы `ОпределитьФактическихИсполнителей` восстановлен по сигнатуре, описанию и вызываемым функциям, но не по реальному BSL-коду.
2. **Значения перечисления ВидыЗамещения** — сервер подтвердил существование перечисления, но не вернул список его значений (Замещающий/Помощник определены косвенно).
3. **Контекст вызова при назначении задачи** — процедура вызывается при "взятии в работу", а не при "назначении" в узком смысле. Это тонкость, которую агент правильно уточнил.

## Паттерны поведения агента

- **Стратегия:** прямой поиск кода → уточнение с фильтром owner → исследование смежных модулей → структура данных. Агент начал с самого эффективного инструмента (`search_code`) и использовал параметр `owner` для фокусировки на конкретных модулях.
- **Retry: 3** — все три из-за неподдерживаемых операций (get_module_text, list_modules, list_tabulars). Агент каждый раз переключался на альтернативный инструмент.
- **Меньше всего вызовов (17)** — самый экономный тест из трёх, при этом ПОЛНОСТЬЮ ответил на вопрос. Это демонстрирует, что для задач поиска кода сервер особенно эффективен.
- **Проблема вызова #11:** search_metadata_by_description вернул 90K символов — агент отметил "слишком большой ответ, не читался". Это потеря 90K символов контекста впустую.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Нет get_module_text | Главная проблема теста — невозможно показать реальный код процедуры. Алгоритм восстановлен по описаниям |
| Огромный ответ search_metadata_by_description (#11) | 90K символов ≈ 162K токенов — половина контекста агента, при этом агент даже не использовал эти данные |
| Нет list_tabulars | Не удалось проверить табличные части справочника ЗамещающиеИПомощники |
| Значения перечислений недоступны | Нет операции для получения значений перечислений |

## Вывод

Сервер `1c-metacode-test-do3` **идеально подходит** для задач поиска процедур по бизнес-описанию. `search_code` с параметром `owner` даёт точные результаты, а комбинация `search_code` + `list_attributes` позволяет восстановить полную картину: функция, её контракт, данные, цепочка вызовов. Единственный серьёзный недостаток — невозможность получить тело функции (get_module_text), из-за чего агент описывает алгоритм, а не показывает код. Из трёх тестов — самый экономный по числу вызовов (17) при полном ответе.
