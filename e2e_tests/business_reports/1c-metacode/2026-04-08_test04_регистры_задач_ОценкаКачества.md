## Что сервер дал хорошо

1. **Полное обнаружение регистров** — через `search_metadata_by_description` найдены оба РН (КоличествоЗадач, КоличествоДействийЗадач) и все ключевые РС (ДействияЗадач, ВсеИсполнителиДействийЗадач, СведенияОбИсполнителяхЗадач, ИсторияЗадач, ЗадачиПоАвторам, ИсторияСобытийЗадач, ПоступившиеОбновленияЗадач).
2. **Полные структуры регистров** — через `list_dimensions` и `list_resources` получены точные структуры: КоличествоЗадач (7 измерений, 9 ресурсов), КоличествоДействийЗадач (10 измерений, 11 ресурсов), ДействияЗадач (3 измерения, 39 ресурсов!).
3. **API-процедуры записи в регистры** — `search_code` нашёл все ключевые процедуры: ЗаполнитьНаборПоДействию, ОбновитьДанныеДействия, ОбновитьДанныеЗадачи для обоих регистров.
4. **Точки входа** — найдена подписка ПриЗаписиЗадачи (ИнтеграцияЗадач), механизм кэшированных данных с очередью для РН КоличествоЗадач.
5. **Операции смены статуса** — полный перечень: УстановитьСостояние, НаправитьНаИсполнение, ОтметитьВРаботе, ОтметитьОтменена, ОтметитьОжидаетПроверки и др.
6. **Асинхронный механизм** — обнаружен ОбработатьОчередьОбновленияКэширующихДанных и ОбновитьКэширующиеДанныеПолностью.

## Что сервер НЕ дал

1. **Тела модулей** — `get_module_text` не поддерживается. Агент видел только сигнатуры и описания, не мог прочитать реальный BSL-код процедур.
2. **Список подписок на события** — `list_modules` не поддерживается. Точный перечень событийных подписок установлен косвенно через `search_code`.
3. **Точный порядок вызовов внутри ПриЗаписиЗадачи** — без тела модуля восстановлен приблизительно.
4. **Точный момент асинхронной записи** — когда именно очередь кэширующих данных обрабатывается (регламентное задание или фоновое) — не удалось определить.

## Паттерны поведения агента

- **Стратегия:** семантический поиск → точечные структуры → код → дополнения. Агент начал с `search_metadata_by_description` для обнаружения регистров, затем получил структуры через template-запросы, затем искал код записи.
- **Минимум шума:** только 2 из 28 вызовов были шумными (list_modules, get_module_text) — агент быстро понял ограничения и переключился на `search_code`.
- **Глубина анализа:** 28 вызовов — агент исследовал не только основные регистры, но и вспомогательные (НаименованияЗадач, Итерации, ИсторияСобытий), а также точки входа через подписки.
- **Бизнес-отчёт отличного качества:** содержит сводную таблицу смены статусов и ASCII-схему зависимостей — высокая ценность для разработчика.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Нет get_module_text | Агент не мог показать "ключевые процедуры" в виде реального кода — только сигнатуры |
| Большой ответ search_metadata_by_description | 65K символов на один запрос — 99 объектов, из которых полезны ~10 |
| Нет list_modules | Невозможно получить список подписок и обработчиков событий объекта |

## Вывод

Сервер показал **лучший результат** по соотношению полезных/шумных вызовов (93% полезных) среди трёх тестов. Для задачи "найти регистры и код, который в них пишет" — отличная комбинация template-запросов (точные структуры) и семантического поиска кода (процедуры и точки входа). Главное ограничение — невозможность прочитать тела модулей, из-за чего агент не смог показать реальный BSL-код, а лишь описал логику по сигнатурам.
