# Оценка качества: TEST-01 — Жизненный цикл входящего документа
**Сервер:** 1c-cloud-embeddings (порт 8000)
**Дата:** 2026-04-07
**Оценщик:** Оркестратор (Claude Opus 4.6)

---

## Общая оценка: ЧАСТИЧНО

## Метрики

| Метрика | Значение |
|---------|----------|
| Вызовов MCP | 13 |
| Полезных (высокая/средняя) | 11 (85%) |
| Шумных (низкая/нерелевантно) | 2 (15%) |
| Retry | 1 |
| Общее время агента | ~6.4 мин |
| Токенов агента (total) | ~180K |

## Что сервер дал хорошо

1. **Архитектурное открытие** — агент правильно определил, что "ВходящееПисьмо" в DO3 — это НЕ `Документ.ВходящееПисьмо` (встроенная почта), а `Справочник.ДокументыПредприятия` с видом документа `ЯвляетсяВходящейКорреспонденцией=Истина` + связанный `Документ.Корреспонденция`. Это ключевое знание, которое code-metadata НЕ раскрыл.
2. **Система нумерации** — найден полный код: `Нумерация.ПолучитьНумераторДокумента()` → `СформироватьЧисловойНомерДокумента()` → `СформироватьСтроковыйНомерДокумента()`. Даже фрагмент кода из `Справочники.ДокументыПредприятия.Модуль`.
3. **Паттерны ПередЗаписью/ПриЗаписи** — восстановлены по смежным объектам: `ОбменДанными.Загрузка`, `УстановитьДополнительноеСвойствоЭтоНовый`, `РаботаСКорреспонденцией.ПередЗаписьюНаСервере`, `РаботаСРабочимиГруппами.ДокументыПередЗаписью`.
4. **Жизненный цикл из справки** — та же цепочка из `ТекущиеСостоянияДокументов`, что и у code-metadata.
5. **Бизнес-процессы** — Рассмотрение, Исполнение, Согласование, Ознакомление, Регистрация.
6. **stats() полезен** — сразу показал что metadata=0, агент не тратил время на бесполезные запросы к metadatasearch (только 1 проверочный).

## Что сервер НЕ дал

1. **Реквизиты документа** — metadata=0, поэтому прямой список реквизитов недоступен. Агент восстановил их из кода (SQL-запросы, заполнение), но это косвенные данные.
2. **Модуль объекта Справочник.ДокументыПредприятия** — сам МодульОбъекта не попал в выдачу codesearch. Обработчики восстановлены по паттернам из других объектов и общих модулей.
3. **Полный список регистров** — найдены основные (ТекущиеСостоянияДокументов, РабочиеГруппы, НастройкиНумерации, ДанныеДокументов, МоиДокументы, СвязиОбъектов), но не те, что привязаны к встроенной почте (ТекстыПисем, ПисьмаВПапках и т.д.). Впрочем, это правильно — агент верно разделил два разных объекта.

## Паттерны поведения агента

- Агент сделал 13 вызовов (vs 18 у code-metadata) — эффективнее.
- Начал с stats() — умный ход, сразу выявил metadata=0 и не тратил время.
- Только 1 проверочный вызов metadatasearch (vs 7 у code-metadata).
- Два вызова вернули огромный объём: #3 (61K) и #10 (80K) — codesearch без ограничения возвращает много шума.
- Качество бизнес-отчёта заметно выше: агент правильно разделил `Документ.ВходящееПисьмо` (почта) и `Справочник.ДокументыПредприятия` (делопроизводство).

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
|----------|------------------------|
| metadata=0 | Коллекция метаданных пуста — metadatasearch бесполезен |
| Огромные ответы codesearch | Два ответа по 60-80K символов — большой расход контекста при среднем качестве |
| Нет ограничения размера ответа | codesearch возвращает всё что нашёл, нет параметра limit на размер |
| Чанкинг 1000 символов | МодульОбъекта ДокументыПредприятия не попал в выдачу — разрезан на фрагменты без контекста |

## Вывод

CloudEmbeddings хорошо работает для **поиска по коду общих модулей** — агент нашёл ключевые процедуры нумерации, регистрации, работы с корреспонденцией. Слабое место — отсутствие метаданных (metadata=0), из-за чего невозможно получить структуру объекта напрямую. Для бизнес-вопроса дал ~65% информации, но более точной с архитектурной точки зрения, чем code-metadata.
