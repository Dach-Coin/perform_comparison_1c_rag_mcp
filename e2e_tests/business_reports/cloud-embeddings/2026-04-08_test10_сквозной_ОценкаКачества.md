## Что сервер дал хорошо

- **Код создания ВходящегоПисьма**: `РаботаСУведомлениями.СоздатьДокумент()` — конкретный BSL-код с заполнением предмета
- **Процесс Рассмотрение**: реквизиты `ОбрабатывающийРезолюцию`, `ВариантОбработкиРезолюции`, `ВариантРассмотрения`; процедура `ПолучитьРезолюцииПоБизнесПроцессу()`
- **Создание задачи Исполнение**: `БизнесПроцессы.Исполнение.МодульОбъекта` — `СоздатьЗадачу()`, `ЗаполнитьПоРассмотрению()` с BSL-кодом
- **Нумерация**: полный цикл `Нумерация.ПолучитьНумераторДокумента()` → `СформироватьЧисловойНомерДокумента()` → `СформироватьСтроковыйНомерДокумента()`
- **Связи документов**: точные имена типов связей `ПисьмоОтправленоВОтветНа`, `ОтправленоОтветноеПисьмо`, `ПолученоОтветноеПисьмо`; API `СвязиОбъектов.УстановитьСвязь()`
- **Замыкание цикла**: `ИнтеграцияЗадач.ОбработатьРегистрациюИсходящегоДокумента()` → `СвязиОбъектов.ПолучитьСвязанныеОбъекты()` → событие для активных задач
- **Отправка по МЭДО и e-mail**: `МЭДО.ОтправитьИсходящийДокумент()`, `ВстроеннаяПочтаСервер.ОтправитьПисьмо()`

## Что сервер НЕ дал

- **Схема реквизитов документов** — metadata коллекция = 0 чанков, невозможно получить список реквизитов ВходящегоПисьма / ИсходящегоПисьма. Агент вынужден был угадывать реквизиты (Организация, Контрагент, КонтактноеЛицо) — часть из них некорректны для данного документа
- **Модуль объекта ВходящегоПисьма** — не найден напрямую, только косвенно через общие модули
- **Код прикрепления файла-ответа** к задаче (шаг 4) — ответ слабый, найдены только `ПрисоединенныеФайлыКлиент.ДобавитьФайлы()` без конкретики привязки к задаче
- **Регистры состояний документов** — `ТекущиеСостоянияДокументов`, `ДанныеБизнесПроцессов` не найдены; агент использовал `ПроцессыДействий` (менее точно)
- **Документация (help)** — 1 запрос к helpsearch дал только общие справки, неполезно

## Паттерны поведения агента

- Начал со `stats` (разумно) → обнаружил metadata=0 → переключился на codesearch
- Стратегия поиска: последовательное расширение запросов по шагам сценария (хорошо)
- 1 retry: metadatasearch → codesearch (обоснованно)
- Чанки codesearch очень большие (до 77K символов) — расход токенов непропорционально высок
- Агент хорошо извлёк конкретные процедуры и BSL-код из больших чанков
- Бизнес-отчёт содержит наглядную схему-диаграмму сквозного сценария
- Качество бизнес-отчёта: хорошее, но реквизиты на шаге 1 частично выдуманы (Организация, Контрагент, КонтактноеЛицо — не существуют в ВходящемПисьме, есть ОтправительАдресат)

## Выявленные проблемы RAG
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Metadata не проиндексирована (0 чанков) | Невозможно получить схему реквизитов документов — ключевой дефицит |
| Непропорционально большие чанки codesearch | До 77K символов в одном ответе, ~140K токенов за один вызов |
| Help-коллекция слабая для бизнес-запросов | 1725 чанков, но на запрос о регистрации/нумерации дала общие справки |
| codesearch не находит модуль объекта документа | Находит общие модули, но не точку входа (ПередЗаписью/ПриЗаписи конкретного документа) |

## Вывод

Сервер cloud-embeddings силён в поиске BSL-кода и конкретных процедур — нашёл основную цепочку модулей сквозного сценария включая нумерацию, связи объектов и замыкание цикла через ИнтеграцияЗадач. Однако отсутствие индекса метаданных делает его непригодным для получения структуры объектов, что критично для сквозного сценария — агент вынужден был домысливать реквизиты документов.
