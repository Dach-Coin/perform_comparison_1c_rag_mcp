## Что сервер дал хорошо

- **Общие модули ЭП** — отлично найдены ключевые модули: `ЭлектроннаяПодпись`, `ЭлектроннаяПодписьКлиент`, `РаботаСЭП`, `СервисКриптографии`, `РаботаСВнешнимПодписанием` — с конкретными именами функций и их сигнатурами
- **Регистр ЭлектронныеПодписи** — через codesearch получена подробная информация о полях регистра (ПодписанныйОбъект, Подпись, КомуВыданСертификат, Отпечаток, ПодписьВерна и др.)
- **Типы подписи** — найдены оба перечисления: `СпособыПодписанияПредметаПроцесса` (ПЭП/УЭП) и `ВидыЭлектронныхПодписей` (Простая/УсиленнаяКвалифицированная)
- **Точки маршрута БП** — подтверждены `Подписать` и `ОбработатьРезультат`
- **Параметры процесса** — через код `ИнтеграцияЗадач` получены реквизиты: Участники, РезультатПодписания, СпособПодписания
- **Штамп ЭП и блокировка** — найдены `ОбновитьОтметкуЭП` и факт блокировки документа после подписания
- **Справочник сертификатов** — `СертификатыКлючейЭлектроннойПодписиИШифрования` найден с описанием формы подписания

## Что сервер НЕ дал

- **Metadata-коллекция пуста (0 записей)** — невозможно получить структуру объектов метаданных напрямую. Это ключевое ограничение, из-за которого агент вынужден восстанавливать реквизиты БП Подписание из фрагментов кода
- **Полная структура ТЧ Участники** — не получены напрямую (только косвенно из кода модулей). Code-metadata нашёл полный набор реквизитов с типами, а cloud — только часть
- **Точный механизм смены статуса документа** — не подтверждён прямой код перехода НаПодписании → Подписан. Агент корректно указал это как неопределённость
- **Табличные части РезультатыПодписания и Этапы** — не описаны (code-metadata и graph нашли их полностью)
- **Константы управления ЭП** — не найдены (graph нашёл: ИспользоватьЭлектронныеПодписи, СоздаватьЭлектроннойПодписиНаСервере и др.)
- **Один файл (вызов #14) оказался слишком большим (~54K символов)** — агент не смог его обработать

## Паттерны поведения агента

- Агент сначала проверил stats (правильно), обнаружил пустую metadata-коллекцию и переключился на codesearch — адекватная стратегия
- Использовал комбинацию codesearch + helpsearch — 10 codesearch, 3 helpsearch, 1 metadatasearch, 1 stats
- Запросы к codesearch были конкретными и целенаправленными — каждый следующий уточнял предыдущий
- Два вызова вернули очень большие ответы (94K и 64K символов) — неэффективное использование контекста
- Retry был только 1 (из metadatasearch в codesearch) — адекватная реакция
- Общий расход контекста (~550K токенов) — самый высокий из трёх серверов, в основном из-за больших чанков кода

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Metadata не проиндексирована | 0 записей → невозможно получить структуру объектов метаданных |
| Нет контроля размера чанков | Вызовы #6 (94K) и #7 (64K) вернули огромные объёмы, большая часть нерелевантна |
| Файл #14 не читаем | 54K символов — агент не смог обработать файл, релевантность неизвестна |
| Код без метаданных = косвенные выводы | Без metadata агент восстанавливает структуру из фрагментов кода — неполно и ненадёжно |
| Helpsearch даёт общую справку | Справка по конкретному БП Подписание не найдена, только общие инструкции по ЭП |

## Вывод

Cloud-embeddings хорошо справляется с поиском кода общих модулей и функций ЭП — нашёл 10+ ключевых модулей с сигнатурами функций. Однако **отсутствие проиндексированной metadata-коллекции** критично ограничивает сервер: невозможно получить структуру БП, реквизиты, ТЧ и перечисления напрямую. Для задач по структуре объектов метаданных сервер не подходит без доиндексации metadata. Для задач по поиску кодовой логики — подходит хорошо, но с проблемой больших чанков.
