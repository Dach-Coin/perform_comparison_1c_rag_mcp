# Оценка качества: TEST-01 — Жизненный цикл входящего документа
**Сервер:** 1c-code-metadata (новый образ 08.04.26)
**Дата:** 2026-04-08
**Оценщик:** Оркестратор (Claude Opus 4.6)

## Что сервер дал хорошо

1. **Полная структура объекта** (get_metadata_details) — 23 реквизита + 4 табличные части за один вызов. Новый инструмент, которого не было в старом образе, дал исчерпывающую структуру.
2. **Граф зависимостей** (graph_dependencies) — 29 рёбер, определены все 6 регистров, обновляемых при работе с письмом. Это ключевой новый инструмент — раньше агент вынужден был гадать по косвенным признакам.
3. **Структура модуля объекта** (get_module_structure) — перечень всех процедур с номерами строк. Позволило точно определить ПередЗаписью (стр. 5-47), ПриЗаписи (49-107).
4. **Структура формы** (get_module_structure) — 131 процедура/функция с номерами строк, включая все обработчики событий формы.
5. **Справка** (helpsearch) — типовая цепочка состояний документа, роли секретаря, сроки регистрации.
6. **Автонумерация** — из metadatasearch получены параметры нумерации: Строка(50), периодичность Год, автонумерация включена.

## Что сервер НЕ дал

1. **Тело процедур ПередЗаписью/ПриЗаписи** объектного модуля ВходящегоПисьма — search_function возвращал обработчики бизнес-процессов, а не документа. Codesearch (vector) тоже не нашёл нужный фрагмент. Codesearch (grep) вернул пустой результат. Причина: фрагменты кода объектного модуля ВходящегоПисьма слишком мало представлены в индексе относительно массы аналогичных обработчиков в бизнес-процессах.
2. **Конкретный код формы** (ПередЗаписьюНаСервере, ПриЗаписиНаСервере) — codesearch (вызов #14) вернул код Корреспонденции вместо ВходящегоПисьма.

## Паттерны поведения агента

- Агент начал с системного вызова stats, затем последовательно: metadatasearch → get_metadata_details → helpsearch → search_function.
- Активно использовал **новые инструменты**: get_metadata_details (#3), get_module_structure (#7, #13), graph_dependencies (#15). Это главное отличие от старого образа.
- При неудаче search_function для ObjectModule (#5) — сделал retry через get_module_structure (#7) и получил структуру модуля. Хорошая стратегия переключения.
- Шумные вызовы (#8, #9, #14) — попытки достать тело кода через codesearch/grep. Vector search приоритизирует бизнес-процессы с такими же именами обработчиков. Grep с составным запросом вернул пустоту.
- Параллельные вызовы (#19 — два codesearch одновременно) — хорошая оптимизация.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Vector search bias к объёмным модулям | search_function для "ПередЗаписью" возвращает только бизнес-процессы (их модули крупнее), игнорируя ObjectModule ВходящегоПисьма |
| Grep не находит по составным запросам | codesearch(use_grep=true) для "ВходящееПисьмо ПередЗаписью" — пустой результат. Возможно, grep ищет строку целиком, а не AND-условие |
| Невозможно получить тело функции по пути | get_module_structure даёт структуру, но не содержимое. Отдельного инструмента "получить тело функции по модулю + строке" нет |

## Вывод

Новый образ code-metadata с расширенным набором инструментов значительно улучшил качество анализа. Ключевые улучшения: get_metadata_details даёт полную структуру за один вызов, graph_dependencies определяет все связанные регистры, get_module_structure даёт перечень процедур с номерами строк. Однако проблема извлечения конкретного тела кода для "не-топовых" модулей осталась — vector search приоритизирует крупные модули бизнес-процессов. Для задач уровня "покажи структуру и связи объекта" сервер подходит отлично; для задач "покажи конкретный код обработчика" — всё ещё зависит от популярности модуля в индексе.
