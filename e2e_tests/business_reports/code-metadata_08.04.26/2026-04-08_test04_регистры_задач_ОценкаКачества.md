## Что сервер дал хорошо

1. **Полные структуры всех 7 регистров** — найдены РН.КоличествоЗадач (9 ресурсов-счётчиков), РН.КоличествоДействийЗадач (11 ресурсов), РС.ДействияЗадач, РС.ВсеИсполнителиДействийЗадач, РС.ЗадачиПоАвторам (30 атрибутов), РС.ИсторияЗадач, РС.ПоступившиеОбновленияЗадач — все через get_metadata_details с полными типами.

2. **Точный код ОбработкаПроведения** — для обоих документов (Задача строки 2698-2727, ДействиеЗадачи строки 470-505) получен через search_function с полными фрагментами кода, включая работу с движениями.

3. **Алгоритм смены статусов** — процедуры УстановитьСостояние (строки 1287-1361) и ОбновитьСостоянияПриИзмененииУчастников (147 строк) найдены с полной логикой переходов между состояниями (Черновик → Новая → ВРаботе → НаПроверке → Закрыта).

4. **Вспомогательные процедуры** — ЗаполнитьНаборПоДействию (логика замещающих), ОбновитьДвиженияДействияЗадачи (обновление без перепроведения), ЗаписатьДоступЗамещающихПоДействиюЗадачи — все найдены с кодом.

5. **Инструменты нового образа** — агент эффективно использовал расширенный набор: get_metadata_details (4 вызова), get_module_structure (1), search_function (7), metadatasearch (4), codesearch (5). Комбинация семантического поиска и точного навигации по структуре дала отличный результат.

## Что сервер НЕ дал

1. **Полный код ПриЗаписи документа Задача** (строки 2093-2696, ~600 строк) — слишком большой для извлечения целиком через search_function. Однако ключевые фрагменты получены через codesearch.

2. **Полная структура РС.ДействияЗадач** — get_metadata_details для этого регистра не был вызван напрямую, структура собрана из metadatasearch (частично) и кода.

## Паттерны поведения агента

- **Стратегия «сверху вниз»**: сначала metadatasearch для обнаружения регистров → get_metadata_details для структур → search_function/codesearch для кода. Логичная и эффективная последовательность.
- **Единственный шумный вызов** (#8, search_function "ОбновитьРегистрыЗадачи") — агент попытался угадать имя функции, не нашёл, и сразу переключился на другую стратегию (get_module_structure). Хорошая реакция.
- **Без retry** — каждый следующий вызов уточнял новый аспект, а не повторял предыдущий.
- **21 вызов за ~5.5 минут** — хороший темп, ~15 сек на вызов в среднем.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Нет проблем чанкинга | get_metadata_details и search_function отдают полные структуры и тела функций |
| Нет проблем навигации | get_module_structure корректно показал все 52 процедуры модуля Задача |
| Ограничение длины | Тело ПриЗаписи (600 строк) не извлечено целиком — ожидаемое ограничение |

## Вывод

Сервер code-metadata нового образа **отлично** справился с задачей поиска регистров и кода. Расширенный набор инструментов (get_metadata_details, get_module_structure, search_function) позволил агенту работать целенаправленно: сначала найти объекты, затем получить их полные структуры, затем точный код. В сравнении со старым образом — заметно более высокое качество за счёт инструментов прямого доступа к метаданным.
