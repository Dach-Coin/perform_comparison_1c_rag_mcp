## Что сервер дал хорошо

- **Полная структура БП.Подписание** — все 20 атрибутов, 7 табличных частей, карта маршрута (53 процедуры + 16 функций) получены за 3 вызова (metadatasearch + get_metadata_details + get_module_structure)
- **Перечисления** — СпособыПодписанияПредметаПроцесса (НаБумаге/ПЭП/УЭП), РезультатыПроцессаПодписания (Подписано/НеПодписано) найдены быстро
- **Справочник ШаблоныПодписания** — полная структура с автоподстановками и условиями, получена за один вызов get_metadata_details
- **Регистр ЭлектронныеПодписи** — главное хранилище ЭП найдено через search_metadata_xml, структура полная (Подпись, Сертификат как ValueStorage, ТипПодписи, ПодписьВерна)
- **Справочник СертификатыКлючей** — найден с реквизитами (ДанныеСертификата, Отпечаток, ДействителенДо, флаг Подписание)
- **Код смены статуса документа** — конкретный фрагмент из ПередЗаписью Справочников.ДокументыПредприятия (ПодписанВсеми → СостоянияДокументов.Подписан)
- **Код завершения БП** — ЗавершениеПриЗавершении и ЗаполнитьИтоговыйРезультатПодписания получены дословно
- **4 модуля ЭлектроннаяПодписьДокументооборот** — группа ОМ для DO3-обёртки над БСП-подсистемой ЭП найдена через search_metadata_xml
- **Функциональная опция ИспользоватьЭлектронныеПодписи** — найдена как переключатель доступности УЭП

## Что сервер НЕ дал

- **Значения перечисления через get_metadata_details** — инструмент возвращает только свойства объекта, не значения перечислений (вызов #10 — низкая релевантность). Агент обошёл это через metadatasearch и codesearch
- **search_function** — ошибка валидации из-за неверной сигнатуры параметров (вызов #18). Агент работал в слепую относительно API, но быстро переключился на codesearch
- **Форма задачи подписывающего** — не исследована UI-часть (как подписывающий взаимодействует с задачей). Это ограничение скорее агента, чем сервера

## Паттерны поведения агента

- **Стратегия «широко → глубоко»**: metadatasearch для обзора → get_metadata_details для структуры → codesearch для кода → search_metadata_xml для ЭП-инфраструктуры
- **Быстрое восстановление после ошибок**: ошибка get_metadata_details (#2) исправлена за 1 вызов (подбор правильного параметра), ошибка search_function (#18) заменена на codesearch (#19)
- **Хороший баланс инструментов**: metadatasearch (5), get_metadata_details (3), codesearch (7), search_metadata_xml (4), get_module_structure (1) — разнообразный набор
- **Минимальный шум**: из 23 вызовов только 3 непродуктивных (2 ошибки параметров + 1 низкая релевантность)

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| get_metadata_details не возвращает значения перечислений | Вызов #10 дал только свойства объекта, а не значения НеПодписано/Подписано |
| search_function — неочевидный API | Ошибка #18: параметры name vs query неочевидны для агента |
| Нет единого запроса «все значения перечисления» | Агенту пришлось комбинировать metadatasearch + codesearch для полного списка |

## Вывод

Новый образ 1c-code-metadata отлично справился с комплексным вопросом о подписании. Сервер обеспечил доступ к метаданным, коду и XML-описаниям через разнообразный набор инструментов (metadatasearch, codesearch, search_metadata_xml, get_metadata_details, get_module_structure). Все подвопросы покрыты: параметры запуска, три способа подписания, хранение ЭП, смена статуса, общие модули. Два сбоя (ошибки параметров) не критичны — агент обходил их за 1 retry.
