## Что сервер дал хорошо

1. **Полная структура справочника Сотрудники** (get_metadata_details) — 9 реквизитов + 2 табличные части с точными типами за один вызов. Аналогично для ФизическиеЛица (7 реквизитов), Должности (1 реквизит), СтруктураПредприятия (6 реквизитов), ЗамещающиеИПомощники (9 реквизитов + 1 ТЧ), Отсутствие (9 реквизитов + 1 ТЧ). Всего 6 вызовов get_metadata_details для справочников — каждый дал полную картину.
2. **Структура регистров** (get_metadata_details x4) — ОсновныеСотрудники, СотрудникиПользователей, ПротоколРаботыСотрудников, ИсполнителиРолейИДелегаты, ДанныеSAPСотрудники. Полные измерения, ресурсы, типы.
3. **Граф зависимостей** (graph_dependencies) — 27 прямых + ~50 обратных связей. Выявлены все ключевые связи и дополнительные (РабочиеГруппы, АдреснаяКнига, ФактическиеИсполнители).
4. **Механизм замещения** — полная цепочка: Документ.Отсутствие → Справочник.ЗамещающиеИПомощники → РегистрСведений.ИсполнителиРолейИДелегаты → ОбщийМодуль.ЗамещающиеИПомощники. Собрана из metadatasearch + get_metadata_details + codesearch.
5. **Код логики Действует** (codesearch) — реальный BSL-код процедуры ЗаполнитьПризнакДействует, показывающий условия: ПометкаУдаления, ДатаНачалаДействия, ДатаОкончанияДействия.
6. **Структура модуля менеджера** (get_module_structure) — 20 процедур/функций, регионы: Обновление, КонтейнерыСотрудников, КонтактнаяИнформация, Фото, ОбработчикиСобытий.

## Что сервер НЕ дал

1. **Детали регистров СотрудникиВКонтейнерах и СотрудникиДляКонтроляСамочувствия** — агент нашёл их через metadatasearch и graph_dependencies, но не углублялся в get_metadata_details. Не критично для бизнес-отчёта.
2. **Регистр "полных прав"** (вызов #12) — вопрос теста подразумевал регистры с правами доступа сотрудников, но в DO3 нет отдельного регистра "полных прав" — есть ИсполнителиРолейИДелегаты с типом ПолныеРоли.

## Паттерны поведения агента

- **Систематичный подход get_metadata_details**: агент последовательно вызвал get_metadata_details для каждого связанного справочника (Сотрудники, ФизическиеЛица, Должности, СтруктураПредприятия, ЗамещающиеИПомощники, Отсутствие) и каждого регистра. Это основное преимущество нового образа — раньше для получения структуры одного объекта нужно было 3-5 вызовов metadatasearch.
- **Минимум шума**: только 2 шумных вызова из 23 (#11 — поиск регистра замещений, #12 — поиск регистра полных прав). Оба — разумные попытки, просто соответствующих объектов нет.
- **Хорошее комбинирование**: metadatasearch для обнаружения объектов → get_metadata_details для углубления → graph_dependencies для полной картины связей → codesearch для кода логики.
- **Расход контекста умеренный** (~60K символов из MCP) — без гигантских search_function.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| metadatasearch не фильтрует точно по object_type | Запрос "замещение сотрудника регистр сведений заместитель" с object_type=РегистрСведений (#11) вернул нерелевантный результат — отдельного регистра замещений нет, но ответ мог быть информативнее |
| Семантический разрыв "полные права" vs "ПолныеРоли" | Запрос "полные права сотрудника доступ" (#12) вернул регистры расширения Диадок вместо ИсполнителиРолейИДелегаты, хотя там используется тип ПолныеРоли |
| Нет проблем с новыми инструментами | get_metadata_details, graph_dependencies, get_module_structure — все отработали корректно |

## Вывод

Тест на справочнике Сотрудники — лучший результат из трёх тестов для нового образа. Агент получил полную картину: структуру 6 справочников, 5 регистров, механизм замещения с кодом, граф зависимостей с 70+ связями. Новый инструмент get_metadata_details радикально упрощает работу — один вызов вместо нескольких metadatasearch. Для задач типа "опиши структуру объекта и его связи" сервер подходит идеально. Слабых мест практически нет — 91% полезных вызовов, и даже "шумные" вызовы были обоснованными попытками.
