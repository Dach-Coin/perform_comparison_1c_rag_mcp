## Что сервер дал хорошо

1. **Полная структура БП Согласование** (get_metadata_details) — все реквизиты, 4 табличные части (Исполнители, РезультатыСогласования, РезультатыОзнакомлений, Предметы) за один вызов. Раньше приходилось собирать это из множества metadatasearch.
2. **Полная структура Справочника.ВизыСогласования** (get_metadata_details) — 14 реквизитов, точные типы и связи с источниками (ДействиеСогласования / ЗадачаИсполнителя / БПСогласование).
3. **Структура модулей** (get_module_structure x3) — ObjectModule (52 процедуры, карта маршрута), ManagerModule (67 экспортных функций), CommonModule РаботаСВизамиСогласования (35 функций). Полный API каждого модуля.
4. **Код логики завершения** (codesearch) — функция ИтоговыйРезультатСогласования с приоритетами НеСогласовано > СогласованоСЗамечаниями > Согласовано. Код СоздатьЗадачиСогласования с логикой вариантов маршрутизации.
5. **Перечисление РезультатыСогласования** — все 3 значения найдены через metadatasearch (за 2 вызова).
6. **Карта маршрута** (из get_module_structure + codesearch) — все точки маршрута: Старт → Подготовка → Согласовать → ОбработкаРезультата → Ознакомиться → Завершение + условия обхода.
7. **Общие модули** — выявлены РаботаСВизамиСогласования, РаботаСПроцессамиПоДействиям, РаботаСПроцессамиПоДействиямСобытия, ИнтеграцияЗадач, РаботаСБизнесПроцессами и др.

## Что сервер НЕ дал

1. **Тело процедуры ЗавершениеПриЗавершении** (строка 1761 ObjectModule) — search_function нашёл эту процедуру в 5 других бизнес-процессах, но не для Согласования. Codesearch (#14) вернул нерелевантные результаты из ЭДО/криптографии.
2. **Детали механизма ОбработкаОчередиЗаданийСервер** — упомянут в контексте отложенной обработки, но полная цепочка вызовов не раскрыта.

## Паттерны поведения агента

- Агент действовал **методично и систематично**: metadatasearch → helpsearch → get_metadata_details → codesearch → get_module_structure. Каждый следующий вызов уточнял предыдущий.
- **Эффективное использование новых инструментов**: 3 вызова get_metadata_details (для БП и Виз), 3 вызова get_module_structure. Это резко сократило количество "слепых" codesearch по сравнению со старым образом.
- Только 1 шумный вызов (#14) из 21 — отличный показатель целенаправленности.
- Retry (#14→#15) — переключение с codesearch на search_function для поиска ЗавершениеПриЗавершении. Стратегия верная, хотя и не дала тело для Согласования.
- **Suммарный расход токенов (~59K символов из MCP)** — умеренный, нет гигантских ответов.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Невозможно получить тело процедуры по модулю+строке | get_module_structure → структура, но не код. ЗавершениеПриЗавершении (стр. 1761) — только заголовок |
| search_function не умеет фильтровать по объекту | Запрос "ЗавершениеПриЗавершении" возвращает одноимённые процедуры из 5 других БП, но не из Согласования |
| codesearch vector bias | Запрос "ЗавершениеПриЗавершении... согласование завершение" (#14) привёл к коду ЭДО/криптографии вместо БП |

## Вывод

Новый образ code-metadata показал отличный результат на тесте согласования. Ключевое преимущество — get_metadata_details и get_module_structure позволяют за 1-2 вызова получить полную структуру объекта/модуля, что раньше требовало 5-8 вызовов metadatasearch+codesearch. Агент получил исчерпывающие данные: структуру БП, визы, перечисления, карту маршрута, ключевой код логики. Единственное слабое место — невозможность извлечь тело конкретной процедуры по имени+модулю, что является архитектурным ограничением (нет инструмента "прочитать код строки N-M модуля X").
