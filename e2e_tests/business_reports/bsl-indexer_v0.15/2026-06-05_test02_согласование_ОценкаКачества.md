# Оценка качества: TEST-02 — Процесс согласования
**Сервер:** bsl-indexer (v0.15.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Все 5 подвопросов закрыты данными из кода: параметры запуска (`ЗаполнитьПоШаблону`, `ЗаполнитьРезультатНастроекПроцесса`, `ОбновитьАктивныйПроцесс`), реквизиты `Catalog.ВизыСогласования`, три значения `Enum.РезультатыСогласования` с маппингом, цепочка завершения (`СогласоватьПриВыполнении` → `ОбходСогласующихЗавершен` → `ЗавершениеПриЗавершении` → `ПриЗавершенииПроцесса`), список общих модулей. Структуру объектов/перечислений пришлось собирать через `grep_body`/`get_function`, т.к. `get_object_structure` снова вернул `attributes=null`.

По поштучной сумме символов из журнала — 93 617 симв / 168 511 ток. **Важно:** два вызова `get_file_summary` (#5, #6) вернули ОШИБКУ «превышение лимита» — дампы ~106K и ~104K символов **НЕ попали в контекст** (инструмент сам отсёк), поэтому в журнальную сумму они входят только как короткие сообщения об ошибке. Использую журнальную сумму как сопоставимую метрику.

## Что сервер дал хорошо
- **`get_stats` подтвердил индекс**: 21 922 файла, 88 737 функций, 4 616 классов, статус ready.
- **Перечисление файлов БП** через `list_files` с `path_prefix` (#4): 18 файлов, ObjectModule.bsl (2281 стр) и ManagerModule.bsl (2402 стр) с числом строк.
- **Полные тела ключевых процедур** через `get_function`: `ИтоговыйРезультатСогласования`, `ОбходСогласующихЗавершен`, `ЗаполнитьПоШаблону` (параметры запуска), `СогласоватьПриВыполнении`, `ЗавершениеПриЗавершении`, `ПриЗавершенииПроцесса`, `СоздатьЗадачиСогласования` (логика 3 вариантов маршрутизации), `ОбновитьАктивныйПроцесс`.
- **`grep_body pattern="%"`** (#9, #10) дал полные списки функций обоих модулей — удобная замена отсутствующей структуры.
- **Реквизиты `ВизыСогласования` через grep** (#19, #43): Документ, Исполнитель, РольИсполнителя, РезультатСогласования, Источник, ПомещенаВИсторию, ИдентификаторУчастника, УстановилРезультат.
- **`grep_code` по маппингу результатов** (#39): три значения перечисления → ВариантыВыполненияПроцессовИЗадач.
- **Кастомизация Тест распознана**: `СогласованоПроверкаУсловия` (роль «ДД Директор по брэнду», `тст_НеОзнакамливать`).
- **Положительное изменение vs TEST-01**: `get_file_summary` на больших модулях вернул контролируемую ОШИБКУ вместо гигантского дампа — катастрофического перерасхода контекста (как в TEST-01 с 160K+118K) в этом тесте НЕ произошло. **Ни одного скачка >20%.**

## Что сервер НЕ дал
- **Структура объектов через `get_object_structure`** — `attributes=null` ТРИЖДЫ: для `BusinessProcess.Согласование` (#2), `Enum.РезультатыСогласования` (#14), `Catalog.ВизыСогласования` (#20). Все реквизиты и значения перечислений пришлось добывать через `grep_body`/`get_function`/`grep_code`.
- **Значения перечислений напрямую** — Enumerations не представлены как отдельные файлы (`list_files **/Enumerations/**` → 0). Состав `РезультатыСогласования` реконструирован из кода, а не из метаданных.
- **Семантический поиск** — `search_function` с `path_glob` по BSL вернул 0 дважды (#7, #8): FTS не отрабатывает с фильтром пути.
- **Надёжный glob в `list_files`** — паттерны `**/BusinessProcesses/Согласование/**`, `**/CommonModules/**`, `**/Enumerations/**` дали 0; рабочим оказался только `path_prefix`. 4 пустых вызова.

## Паттерны поведения агента
- Stateless-модель: каждый вызов с `repo="Тест ДО3"`, без сессии.
- **Научился на TEST-01**: начал с прицельных `get_function`/`grep_body`, а `get_file_summary` применил всего дважды — и оба раза инструмент сам отсёк дамп ошибкой, агент тут же переключился на grep (retry #5-6→7).
- Столкнувшись с `attributes=null`, переключался на `grep_body`/`grep_code` по телу модулей — закрыл вопрос, но ценой лишних вызовов.
- Боролся с неработающим glob: перебирал паттерны `list_files`, прежде чем нашёл `path_prefix` (#3→#4, #27, #29).
- Высокая доля шума (14/44 = 32%): 4× пустой `list_files`, 2× пустой `search_function`, 2× `get_object_structure` с null, 1× пустой `grep_body`, 1× пустой `grep_code`, 1× пустой `get_event_subscriptions`.

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| **`get_object_structure` не отдаёт реквизиты** (`attributes=null`) | ТРИЖДЫ (BusinessProcess, Enum, Catalog) — повтор дефекта из TEST-01; вынудил собирать структуру через grep |
| **Enumerations не индексируются как объекты** | Значения перечислений реконструированы из кода, прямого доступа к составу enum нет |
| **`search_function` + `path_glob` не работает по BSL** | 2 пустых вызова + retry; семантический/FTS-поиск с фильтром пути неэффективен |
| **Ненадёжный glob в `list_files`** | `**/...` паттерны → 0; рабочий только `path_prefix`; 4 пустых вызова |
| Высокая доля шума | 14 из 44 вызовов (32%) — нерелевантны/пусты |
| (улучшение) `get_file_summary` отсекает большие дампы ошибкой | В отличие от TEST-01 — контекст не раздут; **0 скачков >20%** |

## Вывод
bsl-indexer v0.15 закрыл TEST-02 полностью при ≈168K токенов MCP-ответов — это лишь в **~1.17× больше**, чем rlm (144K), и резко ближе, чем разрыв 3.2× в TEST-01. Причина сближения: на этом вопросе сервер избежал гигантских дампов (`get_file_summary` отсёк их ошибкой, `get_event_subscriptions` запрошен с фильтром), поэтому **ни одного скачка >20%**. Остаточный перерасход — структурный: больше вызовов (44 vs 32) и высокая доля шума (32% vs 3%), вызванные двумя повторяющимися дефектами — `get_object_structure` не отдаёт реквизиты (3×) и ненадёжный glob/семантический поиск. Сервер силён для точечного чтения процедур и grep по телу, но для обзора структуры объектов и перечислений по-прежнему требует обходных путей.
