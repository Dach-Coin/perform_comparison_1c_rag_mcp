# Оценка качества: TEST-03 — Структура справочника Сотрудники
**Сервер:** bsl-indexer (v0.15.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ (с оговоркой по замещению)

Реквизиты, обе ТЧ, связи и профильные регистры получены полно и точно — все из сырого XML. Однако по подвопросу «механизм замещения» сервер вывел агента на **устаревший путь** (ТЧ `УдалитьЗаместители` документа Отсутствие с синонимом «(не используется)»), актуальный механизм (`ЗамещающиеИПомощники`) не найден, и часть вывода агент пометил как «додумывание». Поэтому фактически — ПОЛНОСТЬЮ по объёму, но с содержательным пробелом и втрое большим расходом контекста.

## Что сервер дал хорошо
- **`get_stats` подтвердил индекс**: 21 922 файла, 88 737 функций, статус ready.
- **Полная структура справочника из XML** (#4, #6, #8, #11, #18, #22): 9 реквизитов с типами + обе ТЧ (ДополнительныеРеквизиты, КонтактнаяИнформация со всеми колонками) — собрано чтением всех 1712 строк `Сотрудники.xml` по чанкам.
- **Связи подтверждены типами прямо в XML**: Owner=ФизическиеЛица, Должность→Должности, Подразделение→СтруктураПредприятия.
- **Профильные регистры из XML**: ОсновныеСотрудники (ФизЛицо→Сотрудник), ДоступноеВремяСотрудников, ЗанятостьСотрудников, ДанныеSAPСотрудники, ПротоколРаботыСотрудников — с измерениями/ресурсами.
- **`grep_body` по форме** (#20): функции управления регистром ОсновныеСотрудники (ЗаписатьОсновногоСотрудника и др.) — полезная привязка кода к данным.

## Что сервер НЕ дал
- **Структура через `get_object_structure`** — `attributes=null` (#2, известный дефект). Это вынудило прочитать **~12 чанков сырого XML** (`Сотрудники.xml`, `Отсутствие.xml`, 5 регистров) — основной источник расхода 321K токенов.
- **Актуальный механизм замещения** — сервер нашёл только устаревшую ТЧ `УдалитьЗаместители` («(не используется)») в `Document.Отсутствие` и CommonModules/Отсутствия; **справочник `ЗамещающиеИПомощники` (текущий механизм делегирования) НЕ найден**. Вывод «заместители обрабатываются динамически» агент честно пометил как догадку.
- **Поведенческая логика Сотрудников** — ManagerModule (721 стр) и ObjectModule (357 стр) BSL не читались; код заполнения наименования/представлений/параметров сеанса не получен.
- **Полнота регистров** — AccumulationRegisters не проверялись; `ДанныеSAPСотрудники` дочитан лишь частично (200 из 1165 строк).
- **Значения перечислений** — недоступны как метаданные (та же история с Enumerations, что в TEST-02).

## Паттерны поведения агента
- Stateless-модель, `repo="Тест ДО3"` в каждом вызове.
- **Доминирующий паттерн — чтение сырого XML чанками** (16 из 28 вызовов — `read_file`/`list_files`), т.к. `get_object_structure` не отдал реквизиты. Профиль расхода: «смерть от множества чтений», без единичных дампов.
- При поиске замещения упёрся в устаревшую ТЧ и сделал 3 пустых проверочных grep (#24, #25, #28), затем зафиксировал догадку — не дошёл до `ЗамещающиеИПомощники`.
- Подтвердил предупреждённые особенности: `attributes=null`, опора на `path_prefix` вместо `**`-glob.
- **Ни одного скачка >20%** (максимум — #7 list_files регистров ≈10.7%); перерасход накопительный, а не пиковый.

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| **`get_object_structure` не отдаёт реквизиты** (`attributes=null`) | Повтор дефекта (3-й тест подряд) → ~12 чанков сырого XML, ≈321K токенов (2.7× от rlm) |
| **Содержательный пробел по замещению** | Найден устаревший путь (`УдалитьЗаместители`), актуальный `ЗамещающиеИПомощники` пропущен; вывод частично угадан |
| Перечисления/структурные метаданные недоступны | Всё собирается из сырого XML, дорого по контексту |
| Неполнота охвата | BSL-модули объекта, AccumulationRegisters, полный SAP-регистр не прочитаны |
| Малая доля шума | 3 пустых grep при поиске несуществующего регистра заместителей |

## Вывод
bsl-indexer v0.15 дал точные реквизиты, ТЧ, связи и профильные регистры справочника Сотрудники — но всё через **чтение сырого XML**, т.к. `get_object_structure` снова вернул `attributes=null` (дефект повторяется третий тест подряд). Расход — ≈321K токенов, в **~2.7× больше** rlm (118K). Хуже того, по ключевому подвопросу о замещении сервер вывел на устаревшую структуру и не нашёл актуальный `ЗамещающиеИПомощники`, из-за чего часть ответа агент был вынужден угадать. На структурно-обзорных задачах с большими XML и «спрятанной» в коде бизнес-логикой сервер проигрывает RLM-подходу и по стоимости, и по точности. Силён он для прицельного чтения конкретного файла/функции, а не для целостного обзора объекта и его механизмов.
