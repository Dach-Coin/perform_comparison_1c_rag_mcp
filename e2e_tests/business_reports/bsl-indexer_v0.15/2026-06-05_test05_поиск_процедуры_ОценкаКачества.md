# Оценка качества: TEST-05 — Поиск процедуры по бизнес-описанию
**Сервер:** bsl-indexer (v0.15.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Искомая процедура найдена и подтверждена: `ОпределитьФактическихИсполнителей` в `CommonModules/РаботаСЗадачами/Ext/Module.bsl` (стр. 24–251), прочитан полный код, найдены все 6 вызывающих в 5 модулях. **Это первый тест, где bsl-indexer обошёл rlm** — и по числу шагов до цели (3 vs 9), и по суммарному контексту (58.6K vs 89.3K токенов).

## Метрики
| Метрика                | Значение |
| ---------------------- | -------- |
| Вызовов MCP            | 6 |
| Полезных               | 4 (67%) |
| Шумных                 | 2 (33%) — #2 search_terms пусто, #5 get_callers пусто |
| Retry                  | 2 (search_terms→search_function; get_callers→grep_body) |
| **Вызовов до цели**    | **3** (целевая функция в #3) |
| Общее время агента     | ~2.5 мин |
| Σ символов из MCP      | 32 558 |
| Токены MCP-ответов (×1.8) | ≈58 604 |
| Токенов агента (self-est.) | input ~85K, output ~6K |

## Что сервер дал хорошо
- **FTS `search_function` сразу попал в цель** (#3): по запросу «замещение исполнитель задача» целевая `ОпределитьФактическихИсполнителей` вернулась в топе из 5 функций. Лексический полнотекстовый поиск по смыслу-через-ключевые-слова — **сильная сторона bsl на этом классе задач**.
- **`get_function` дал полный код** (#4): модуль, строки 24–251, экспортная — для разбора «как работает» (три уровня: прямой сотрудник → роль через РС.ИсполнителиРолей → замещение через Справочник.ЗамещающиеИПомощники).
- **`grep_body` нашёл всех вызывающих** (#6): 7 вхождений в 5 модулях с именами функций и строками (ПринятьКИсполнению, ВзятьВРаботу, ЗаполнитьФактическогоИсполнителя, 2× РаботаСВнешнимПодписанием, ЭскалацияЗадач).
- **Минимум шагов**: всего 6 вызовов, ~2.5 мин — самый быстрый прогон среди всех тестов.

## Что сервер НЕ дал
- **`search_terms` не работает без LLM-обогащения** (#2): «enrich для этого репо не выполнен» → пустой результат. Семантический слой не активирован.
- **`get_callers` не видит вызовы через квалифицированное имя** (#5): вызовы вида `РаботаСЗадачами.ОпределитьФактическихИсполнителей` граф не отследил → 0; пришлось обходить через `grep_body`.
- **Нет дерева вызовов вглубь**: список вызывающих — плоский (1 уровень). Цепочку «UI-форма → ВзятьВРаботу → целевая» (2 уровня), которую дал rlm, bsl не строил.

## Паттерны поведения агента
- Stateless, `repo="Тест ДО3"`. Чёткая стратегия «поиск → тело → вызывающие».
- Два retry, оба сработали мгновенно: search_terms→search_function (FTS), get_callers→grep_body.
- **Профиль расхода спайковый**: 2 крупных ответа — `search_function` (#3, ~18.5K симв = 57% контекста, ⚠️) и `get_function` (#4, ~9.2K = 28%, ⚠️). Минимум вызовов, но контекст сосредоточен в двух дампах.

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| ⚠️ `search_function` отдаёт крупный дамп | #3 ≈18.5K символов (5 функций с телами) = 57% контекста за один вызов |
| ⚠️ `get_function` крупный | #4 ≈9.2K = 28% контекста |
| `search_terms` требует enrich | #2 пусто — семантический слой не активирован для репо |
| `get_callers` не видит квалифицированные вызовы | #5 пусто (вызовы через `Модуль.Функция`) → обход через grep_body |

## Вывод
На задаче «найти процедуру по бизнес-описанию» bsl-indexer v0.15 показал **лучший результат, чем rlm**: целевая `ОпределитьФактическихИсполнителей` найдена FTS-поиском `search_function` с первой попытки (вызов #3), за 6 вызовов и ≈58.6K токенов против 16 вызовов и 89.3K у rlm. Это естественная сильная сторона лексического индекса — отображение «ключевые слова → функция». Минусы: `search_function` возвращает крупные дампы (два ⚠️-всплеска), `search_terms` без enrich мёртв, а `get_callers` не видит вызовы через квалифицированное имя (обход через grep_body даёт плоский список без дерева вглубь). Для точечного поиска кода по описанию — отличный инструмент; для построения иерархии вызовов уступает RLM.
