## 1. Реквизиты справочника с типами

Справочник `Catalog.Сотрудники` является подчинённым (Owners: `Catalog.ФизическиеЛица`) — это ключевой архитектурный факт: один сотрудник = одна запись в Сотрудники + одна запись-владелец в ФизическиеЛица.

Стандартные реквизиты (от платформы):
| Реквизит | Синоним | Тип |
|---|---|---|
| Description | ФИО | String(150) |
| Owner | Физическое лицо | CatalogRef.ФизическиеЛица |
| Code | Код | String |
| Parent | Родитель | CatalogRef.Сотрудники |

Пользовательские реквизиты (из XML, блок ChildObjects):
| Реквизит | Синоним | Тип | Обязателен |
|---|---|---|---|
| ГрафикРаботы | График работы | CatalogRef.ГрафикиРаботы | Нет |
| ДатаНачалаДействия | Дата начала действия | Date | Нет |
| ДатаОкончанияДействия | Дата окончания действия | Date | Нет |
| Действует | Действует | Boolean | Нет (индексируется) |
| Должность | Должность | CatalogRef.Должности | **Да (ShowError)** |
| Подразделение | Подразделение | CatalogRef.СтруктураПредприятия | **Да (ShowError)**, индексируется |
| Помещение | Помещение | CatalogRef.ТерриторииИПомещения | Нет |
| ПредставлениеВДокументах | Представление в документах | String(переменная) | Нет |
| ПредставлениеВПереписке | Представление в переписке | String(переменная) | Нет |

Комментарий из XML справочника: «Содержит сотрудников на определенных должностях в структурных единицах.»

Блокировка данных настроена на пару полей `Owner` (ФизЛицо) + `Должность`.

## 2. Табличные части

Справочник имеет **две** табличные части:

### 2.1. ДополнительныеРеквизиты
Стандартная механика подсистемы «Дополнительные реквизиты и сведения» (БСП).
| Колонка | Тип |
|---|---|
| Свойство | ChartOfCharacteristicTypesRef.ДополнительныеРеквизитыИСведения |
| Значение | Characteristic.ДополнительныеРеквизитыИСведения |
| ТекстоваяСтрока | String (полный текст строкового допреквизита) |

Набор называется `Справочник_Сотрудники` (поле ИмяПредопределенногоНабора).

### 2.2. КонтактнаяИнформация
Стандартная механика подсистемы «Контактная информация».
| Колонка | Тип |
|---|---|
| Тип | EnumRef.ТипыКонтактнойИнформации |
| Вид | CatalogRef.ВидыКонтактнойИнформации |
| Представление | String(500) — для отображения в формах |
| ЗначенияПолей | String — служебное хранилище XML |
| Страна | String(100) |
| Регион | String(50) |
| Город | String(50) |
| АдресЭП | String(100) — e-mail |
| ДоменноеИмяСервера | String(100) |
| НомерТелефона | String(20) |
| НомерТелефонаБезКодов | String(20) |
| ВидДляСписка | CatalogRef.ВидыКонтактнойИнформации |
| Значение | String — служебное |

Типы контактной информации фильтруются через предопределённый элемент `Catalog.ВидыКонтактнойИнформации.СправочникСотрудники`.

## 3. Связи с другими справочниками

### 3.1. Catalog.ФизическиеЛица — связь «Владелец»
- Сотрудники подчинены ФизическиеЛица через стандартный атрибут `Owner`.
- Регистр **ОсновныеСотрудники** (InformationRegister, непериодический, независимый) реализует обратную навигацию: измерение `ФизическоеЛицо` (CatalogRef.ФизическиеЛица) → ресурс `Сотрудник` (CatalogRef.Сотрудники). Это позволяет получить «основного» (актуального) сотрудника по физическому лицу.
- В форме элемента Сотрудника есть функции `ЗаполнитьОсновнойСотрудникПриЧтении`, `ЗаписатьОсновногоСотрудникаПриИзменении`, `НастроитьДоступностьОсновнойСотрудник`, явно управляющие записью в этот регистр.
- Один человек (ФизЛицо) может иметь несколько записей Сотрудников (разные должности/периоды), регистр ОсновныеСотрудники хранит «текущую» запись.

### 3.2. Catalog.Должности — прямая ссылка
- Реквизит `Должность` (тип `CatalogRef.Должности`) — обязателен к заполнению.
- Включён в DataLockFields вместе с Owner, что означает контроль параллельного доступа по паре (ФизЛицо + Должность).
- Команда `СотрудникиДолжности` (навигационная панель) позволяет перейти из карточки должности к списку сотрудников.

### 3.3. Catalog.СтруктураПредприятия — прямая ссылка
- Реквизит `Подразделение` (тип `CatalogRef.СтруктураПредприятия`) — обязателен, индексируется.
- Команда `СотрудникиПодразделения` (навигационная панель) позволяет перейти из карточки подразделения к списку сотрудников.
- Формы `ФормаСотрудниковПодразделения` и `ФормаСотрудниковДолжности` — специализированные списки с группировкой.

## 4. Механизм замещения сотрудников

### 4.1. Документ «Отсутствие» — основной носитель
Механизм замещения реализован через документ `Document.Отсутствие`. Его ключевые реквизиты:
| Реквизит | Тип | Назначение |
|---|---|---|
| Сотрудник | CatalogRef.Сотрудники \| CatalogRef.Пользователи | Кто отсутствует |
| ВидОтсутствия | CatalogRef.ВидыОтсутствий | Причина (обязателен) |
| ДатаНачала | DateTime | Начало отсутствия |
| ДатаОкончания | DateTime | Окончание отсутствия |
| ВесьДень | Boolean | Полный день |
| Автор | CatalogRef.Сотрудники \| CatalogRef.Пользователи | Кто ввёл |
| Комментарий | String | Пояснение |
| БудуРазбиратьЗадачи | Boolean | Синоним «Буду на связи» |

### 4.2. Табличная часть заместителей
В XML документа присутствует ТЧ `УдалитьЗаместители` с синонимом **(не используется) Заместители**. Колонки: `Заместитель` (CatalogRef.Сотрудники|Пользователи) и `Комментарий`. Эта ТЧ **устарела и не используется в текущей версии**.

### 4.3. Актуальный механизм заместителей
Заместители в актуальной схеме обрабатываются **динамически** через общие модули:
- `CommonModules/Отсутствия` — содержит `ПолучитьПредставлениеЗаместителей`, которая строит представление по тексту запроса к документу Отсутствие.
- `CommonModules/ИнтеграцияЗадач` — получает заместителей при обработке задач: «Получим заместителей и предложим выбор, если заместители указны».
- `CommonModules/ДействияСерверПовтИсп` — «Получим заместителей и помощников».

Вывод: заместители задаются не в отдельном регистре, а хранятся в самом документе Отсутствие и выбираются через запросы к нему при маршрутизации задач и поручений.
