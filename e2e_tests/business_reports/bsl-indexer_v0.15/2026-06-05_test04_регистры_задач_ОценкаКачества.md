# Оценка качества: TEST-04 — Регистры, обновляемые при работе с задачами
**Сервер:** bsl-indexer (v0.15.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ (с пробелами охвата)

Оба регистра накопления и три регистра сведений описаны со структурами, прочитан реальный код-писатель (ОбработкаПроведения/ПриЗаписи/RecordSetModule). Однако охват уже, чем у rlm: регистр `ИсторияЗадач` не исследован, ресурсы `ДействияЗадач` прочитаны лишь на 1/3 (170–600 из 1987 строк), а точные ±1-переходы по статусам агент частично вывел логически. Достигнуто ценой ≈418K токенов с одним ⚠️-дампом.

## Метрики
| Метрика                | Значение |
| ---------------------- | -------- |
| Вызовов MCP            | 33 |
| Полезных               | 30 (91%) |
| Шумных                 | 3 (9%) — #5 null, #11 пустой grep, #27 пустой |
| Retry                  | 1 (#11→12: XML не grep-ается) |
| Общее время агента     | ~12 мин |
| Σ символов из MCP      | 232 506 |
| Токены MCP-ответов (×1.8) | ≈418 511 |

> Цифры по журнальной сумме (232 506 симв / 418 511 ток); агент в логе оценил ~245 680 симв / ~442 224 ток. Беру журнальную сумму как сопоставимую метрику (per-call значения приблизительные). В **~2.3× больше**, чем у rlm (185K) на тот же вопрос.

## Что сервер дал хорошо
- **`health` + `get_stats`** подтвердили живость и индекс (21 922 файла, ready).
- **Полные структуры РН из XML**: `КоличествоЗадач` (7 измерений, 9 ресурсов-счётчиков) и `КоличествоДействийЗадач` (10 измерений, +ВСрок/Истекающих/ПоступилиОбновления) — собрано чтением XML по чанкам.
- **Реальный код-писатель** через `grep_body` по имени регистра + `get_function`: `ОбработкаПроведения` (Задача, ДействиеЗадачи), `ПриЗаписи` (Задача), `RecordSetModule.ОбновитьДанныеЗадачи`/`ОбновитьДанныеДействия`, `ЗаполнитьНаборПоДействию` (учёт замещающих из ВсеИсполнителиДействийЗадач).
- **`grep_body` по имени регистра** оказался эффективным для вопроса «кто пишет» — нашёл документы-писатели без спец-инструмента.
- **РС `ВсеИсполнителиДействийЗадач`** прочитан целиком: измерения ДействиеЗадачи/Исполнитель/Основание(ЗамещающиеИПомощники).
- **Регламентное задание** `ОбслуживаниеИтоговЗадач` (пересчёт итогов РН) и `ОбработатьИзменениеСостоянияЗадачи`.

## Что сервер НЕ дал
- **⚠️ Дамп `list_files InformationRegisters`** (#4) — 200 файлов, **66 426 символов**, «превышен лимит». Агент сохранил вывод в файл и **разобрал его Python’ом вне протокола** (серая зона, как в TEST-01). Один вызов = 27% всего контекста теста.
- **Структура через `get_object_structure`** — снова `attributes=null` (#5), вынудило читать сырой XML регистров по чанкам.
- **Регистр `ИсторияЗадач`** — не исследован (rlm его покрыл); событийные записи (Закрыта/ПеренесенСрок/ЗакрытаПодзадача) не получены.
- **Полные ресурсы `ДействияЗадач`** — прочитана только 1/3 файла (170–600 из 1987 строк); 40 ресурсов целиком не подтверждены.
- **Точные изменения по статусам** — частично «додуманы»: переходы ±1 в ресурсах выведены логически из RecordSetModule, без обхода всех методов Отметить*.

## Паттерны поведения агента
- Stateless-модель, `repo="Тест ДО3"`.
- **Нет спец-инструмента под регистры** — вопрос «кто пишет» решал через `grep_body "ИмяРегистра" в BSL` + `get_function`. Работает, но требует ручной навигации и чтения XML для структур.
- `get_object_structure` → null → ~10 чанков сырого XML (доминирующий источник расхода).
- Один retry (#11→12): `grep_text` по XML дал 0 (XML индексируется как code) → переключение на `read_file`.
- **Внепротокольный Python-обход** для разбора 66K-дампа списка регистров — признак, что инструмент отдал данные непригодно для прямого использования.
- Один ⚠️-скачок (#4, 27%); остальной расход — накопительный от множества `read_file`.

## Выявленные проблемы
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| **⚠️ `list_files` отдал 66K-дамп** (200 регистров) | #4 = 27% контекста; потребовал внепротокольного Python-разбора |
| **`get_object_structure` не отдаёт реквизиты** (`attributes=null`) | Повтор дефекта (4-й тест подряд) → чтение сырого XML регистров по чанкам |
| **Уже охват, чем у rlm** | `ИсторияЗадач` пропущен; `ДействияЗадач` прочитан на 1/3; статусные ±1 частично угаданы |
| Нет инструмента «писатели регистра» | «Кто пишет» добывалось через grep по имени + чтение кода вручную |
| `grep_text` не работает по XML | #11 пустой → retry |

## Вывод
bsl-indexer v0.15 дал корректные структуры обоих РН и трёх РС и прочитал реальный код-писатель, подтвердив правильную картину — но ценой ≈418K токенов (**~2.3× от rlm**, 185K), с одним ⚠️-дампом `list_files` (66K, 27% контекста) и внепротокольным Python-разбором. Охват вышел уже: `ИсторияЗадач` не исследован, `ДействияЗадач` прочитан частично, часть статусной логики угадана. Корень — отсутствие регистро-ориентированных инструментов (аналога `find_register_writers`/`find_register_movements`) и `attributes=null`, из-за чего и «кто пишет», и «какая структура» решаются через grep + чтение сырого XML. Сервер справился, но на задачах про движения регистров уступает RLM-подходу и по стоимости, и по полноте.
