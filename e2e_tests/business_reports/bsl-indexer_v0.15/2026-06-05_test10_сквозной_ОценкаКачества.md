# Оценка качества: TEST-10 — Сквозной сценарий (письмо → резолюция → задача → ответ)

**Сервер:** bsl-indexer (v0.15.0)
**Дата:** 2026-06-05
**Оценщик:** Оркестратор (Claude Opus 4.8, 1M context)

## Общая оценка: ПОЛНОСТЬЮ

Все 5 шагов покрыты реальным кодом: `Document.ВходящееПисьмо` (ObjectModule/ManagerModule — ПередЗаписью/ПриЗаписи, РС КоличествоПисемВПапках/СведенияОбАдресатах/HTMLПредставленияСодержанияПисем), **`Catalog.Резолюции`** (объект + модуль `РаботаСРезолюциями.ПолучитьРезолюции`), `BusinessProcess.Исполнение` → `Task.ЗадачаИсполнителя` (`ВыполнениеЗадачСервер.ВыполнитьЗадачу`, РС ЗадачиДляВыполнения + **кастомные тст_-регистры**), `Document.ИсходящееПисьмо` (цепочка «Ответить»: Commands/Ответить → `ВстроеннаяПочтаКлиент.ОтветитьНаПисьмо` → форма → `ЗаполнитьСтруктуруРеквизитовПоПисьму`, ТипОтвета=ОтветНаПисьмо, ветки переписки `ПисьмаВеток`/`ВеткиПереписки`). 35 вызовов, ≈217K токенов контекста, без ⚠️. Уникальная глубина — **слой кастомизации Тест**, который rlm не вскрыл.

> **Сверка с исходником (оркестратор):** подтверждено прямым чтением — `Catalogs\Резолюции.xml` существует (**bsl верно назвал объект шага 2** — `Catalog.Резолюции`, чего rlm не сделал), кастомные регистры реальны: `тст_СрокиИсполненияЗадач.xml`, `тст_СогласованиеЗаявокСБ.xml`, `тст_ИзмененияОценкиРискаКонтрагентов.xml` — все на месте (bsl нашёл их чтением ObjectModule ЗадачаИсполнителя). **Пробел шага 2:** bsl не раскрыл `BusinessProcess.Рассмотрение` (он существует — `BusinessProcesses\Рассмотрение.xml`) — то есть назвал *объект-справочник* резолюции, но пропустил *процесс* её вынесения. rlm — зеркально: разобрал процесс, но не назвал объект. Шаг 2 у обоих закрыт зеркально-частично; bsl сильнее в реальном коде и кастомизации, слабее в систематике процессов/регистров.

(2) Агент в итоге написал «реально в контексте ~29 850 симв» — это арифметическая ошибка: его же таблица суммируется в **120 705 симв**; беру журнальную сумму. С телом overflow было бы ≈377K — guard сэкономил ~159K токенов.

## Что сервер дал хорошо
- **Реальный код каждого шага** (ObjectModule диапазонами): ВходящееПисьмо ПередЗаписью/ПриЗаписи (#5, #6) с РС КоличествоПисемВПапках/СведенияОбАдресатах; ИсходящееПисьмо ПриЗаписи (#26) с НеОтправленныеИсходящиеПисьма/ПисьмаВеток.
- **Точная идентификация объекта шага 2** (#9, #10, #11): `Catalog.Резолюции` (Справочник, ObjectModule 95 стр) + модуль `РаботаСРезолюциями.ПолучитьРезолюции` (полный запрос: АвторРезолюции, ВнесРезолюцию, ДатаРезолюции, Документ, Источник, Подписана, ФактическийАвтор, LEFT JOIN ЭлектронныеПодписи) — **то, что rlm не назвал**.
- **Кастомизация Тест — уникальная находка** (#18, #19): при ПриВыполнении/ПриЗаписи ЗадачаИсполнителя пишутся `тст_СогласованиеЗаявокСБ`, `тст_ИзмененияОценкиРискаКонтрагентов`, `тст_СрокиИсполненияЗадач` (+ КешИнформацииОбОбъектах, ПроцессыДействий) — **подтверждено сверкой**, rlm этот слой не вскрыл.
- **Чистая цепочка «Ответить»** (#29–34): Commands/Ответить → `ВстроеннаяПочтаКлиент.ОтветитьНаПисьмо` → форма ИсходящегоПисьма (Команда=Ответить, Письмо=<ВходящееПисьмо>) → `СформироватьСтруктуруРеквизитовПисьма` → `ЗаполнитьСтруктуруРеквизитовПоПисьму` (отправитель→получатель, тема Re:, ТипОтвета=ОтветНаПисьмо, ПисьмоОснование).
- **Ветки переписки** (#32): `ОпределитьВеткуДляЧерновика` → РС `ПисьмаВеток` + Справочник `ВеткиПереписки` (новое письмо → новая ветка; с основанием → ветка входящего) — деталь, которую rlm не выделил.
- **ВыполнитьЗадачу детально** (#16): `ВыполнениеЗадачСервер.ВыполнитьЗадачу` (права, ДатаИсполнения/ТекущийИсполнитель/РезультатВыполнения, ОбработкаОчередиЗаданийСервер, событие ПриВыполненииЗадачиСПараметрами; фон через РС ЗадачиДляВыполнения).
- **Подтверждение регистров отправки** (#35): `grep_code` по 5 регистрам писем — НеОтправленныеИсходящиеПисьма (ЗарегистрироватьНеуспешнуюПопытку/ЗакончилисьПопыткиОтправки), КоличествоПисемВПапках, ПисьмаВеток, HTMLПредставленияСодержанияПисем, СведенияОбАдресатах.

## Что сервер НЕ дал
- **`BusinessProcess.Рассмотрение`** — процесс шага 2 не раскрыт (существует, но bsl остановился на справочнике Резолюции + модуле). Зеркальный пробел к rlm.
- **`Document.Задача`** — отдельный документ-задача не разобран (bsl пошёл по ветке БП Исполнение → ЗадачаИсполнителя; Document.Задача с его ТЧ Приложения/Участники не охвачен).
- **Систематика регистров** — регистры найдены точечно (по упоминаниям в коде), без полного обзора измерений/ресурсов, который дал rlm через `tree`/`parse_object_xml`.
- **Регл. задания** — не перечислены явно (rlm дал 5 активных РЗ).
- **Механизм файла-ответа** — `РаботаСФайлами` не исследован (самооценка агента); UI-формы рассмотрения/резолюции не читались.

## Паттерны поведения агента
- Stateless, `repo="Тест ДО3"`. Стратегия: `list_files` → `read_file` ObjectModule диапазонами → `get_function`/`search_function` → `grep_body`/`grep_code` для подтверждений. Сильно на **реальном коде**, слабее на метаданных-структурах.
- 2 retry (#15→16 path_glob дал 0 → без фильтра; #22→23 FTS пуст → grep_body). 5 шумных вызовов: #3 null-структура, #15/#22/#24 пустые FTS на строгих запросах, #27 пустой get_event_subscriptions (русское имя события).
- **get_object_structure снова `attributes=null`** (#3) → весь разбор структур пошёл через сырой код/XML.
- **get_event_subscriptions overflow** (#28, 88 975 симв) → guard сохранил в tmp; агент дочитал PowerShell-ом (вне MCP). В контекстной таблице — без ⚠️ (макс #7 get_file_summary ≈14.8%); без guard был бы скачок ~41%.
- Быстрый прогон — **5:51 wall-clock** против 22 мин у rlm.

| Нет систематики регистров и регл. заданий | точечно из кода, без полной карты (это дал rlm) |

## Вывод
bsl-indexer v0.15 закрыл TEST-10 полностью и **глубже всех залез в реальный код шагов**: точно назвал объект `Catalog.Резолюции` (чего rlm не сделал), вскрыл **слой кастомизации Тест** (тст_СрокиИсполненияЗадач/тст_СогласованиеЗаявокСБ/тст_ИзмененияОценкиРискаКонтрагентов — подтверждено сверкой), дал чистую цепочку «Ответить» с ветками переписки. Зеркальный пробел к rlm — пропущен `BusinessProcess.Рассмотрение` (процесс шага 2) и не разобран `Document.Задача`; регистры/регл.задания поданы точечно, без систематики. По токенам — почти паритет с rlm (217K против 204K, +7%) и **вдвое-втрое быстрее по времени** (5:51 против 22 мин); guard `get_event_subscriptions` снова удержал overflow (≈159K токенов) вне контекста. Итог: **ПОЛНОСТЬЮ** — для глубины конкретного кода и обнаружения кастомизации bsl сильнее; для системной карты процессов/регистров/заданий полнее rlm. Тест демонстрирует их взаимодополняемость лучше всех в серии.
