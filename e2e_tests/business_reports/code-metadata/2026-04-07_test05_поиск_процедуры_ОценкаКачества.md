## Что сервер дал хорошо

- **Быстрая идентификация**: первый же `codesearch` по запросу «фактические исполнители задачи замещения» нашёл модуль `РаботаСЗадачами` и связанные объекты. Точное имя функции `ОпределитьФактическихИсполнителей` подтверждено на 2-м запросе.
- **Точная сигнатура**: 3-й запрос вернул полную сигнатуру с указанием файла `CommonModules/РаботаСЗадачами/Ext/Module.bsl` и номером чанка.
- **Детали алгоритма по чанкам**: 4-й запрос вернул ключевые чанки (chunk_2, 4, 7, 8, 9) с инициализацией, ролевой веткой, замещениями и возвратом результата.
- **Граф вызовов**: 5-й запрос нашёл все точки вызова. 8-й запрос уточнил контекст `ВзятьВРаботу`.
- **Вспомогательные объекты**: `metadatasearch` (#6) дал структуру справочника `ФактическиеИсполнители` с реквизитами и типами. `codesearch` (#7) нашёл полный код `НайтиСоздатьФактическогоИсполнителя`. `codesearch` (#10) подтвердил цепочку до `АктуальныеЗамещенияПоДействиямЗадач`.
- **Самый детальный бизнес-отчёт**: агент собрал наиболее подробное описание алгоритма из всех трёх серверов — с конкретным кодом каждой ветки, таблицей реквизитов `ФактическиеИсполнители`, бизнес-правилами и схемой вызовов.

## Что сервер НЕ дал

- **helpsearch бесполезен** (вызов #9): вернул шаблоны инструкций и справку по фоновым заданиям — документация по механизму фактических исполнителей отсутствует в help-коллекции.
- **Полный текст функции**: как и у cloud-embeddings, тело разбито на чанки (chunk_1 — chunk_9), порядок чанков не всегда очевиден.

## Паттерны поведения агента

- **Глубокое исследование**: 10 вызовов vs 6 у cloud-embeddings. Агент дополнительно запросил структуру справочника `ФактическиеИсполнители` (metadatasearch), код `НайтиСоздатьФактическогоИсполнителя`, код `АктуальныеЗамещенияПоДействиямЗадач`, контекст `ВзятьВРаботу`. Это дало более полную картину.
- **Один разведочный вызов** (helpsearch #9): осознанная попытка найти документацию, не удалась — но это допустимая стратегия (1 шумный из 10).
- **Нет retry**: каждый следующий запрос строился на результатах предыдущего, не было тупиков.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Чанкинг больших функций | Тело функции разбито на ~9 чанков (chunk_1 — chunk_9), порядок восстанавливался логически. |
| Пустая help-коллекция по теме | helpsearch не содержит документации по механизму замещений и фактических исполнителей. |
| Нумерация чанков | Агент видит chunk_1, chunk_2 и т.д., но не может запросить конкретный чанк — приходится подбирать запросы, чтобы получить нужные фрагменты. |

## Вывод

code-metadata — **отличный сервер для глубокого анализа кода с дополнительным контекстом метаданных**. Он нашёл функцию так же быстро, как cloud-embeddings, но дополнительно предоставил структуру связанных справочников через `metadatasearch`. Бизнес-отчёт оказался самым подробным из трёх. Чуть больше вызовов (10 vs 6), но и больше фактов. Единственная слабость — helpsearch не содержит релевантной документации.
