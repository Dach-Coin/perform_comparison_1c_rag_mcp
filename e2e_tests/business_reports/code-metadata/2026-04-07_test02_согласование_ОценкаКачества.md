## Что сервер дал хорошо

1. **Полная структура метаданных БП Согласование** — metadatasearch работает и вернул:
   - Все реквизиты объекта: Наименование, Описание, ВариантСогласования (обязательный), РезультатСогласования, Состояние
   - Табличные части: Исполнители, РезультатыСогласования, Предметы, ПредметыЗадач, ДополнительныеРеквизиты
   - Реквизиты ТЧ Исполнители: ВариантУстановкиСрокаИсполнения, ПорядокСогласования, ЗадачаИсполнителя
   - Основная форма: ФормаБизнесПроцесса

2. **Перечисления — полный набор значений с синонимами:**
   - ВариантыМаршрутизацииЗадач: Последовательно ("По очереди"), Параллельно ("Всем сразу"), Смешанно
   - ПорядокВыполненияЗадач: ПослеПредыдущего, ВместеСПредыдущим
   - РезультатыСогласования: Согласовано, СогласованоСЗамечаниями, НеСогласовано

3. **Справочник ВизыСогласования** — полная структура из metadatasearch:
   - Документ (ДокументыПредприятия), Источник (составной тип: ДействияСогласования | ЗадачаИсполнителя | БП.Согласование)
   - РезультатСогласования, ДатаСоздания, ДатаИсполнения
   - Связь с ФО ИспользоватьВизыСогласования и Константой

4. **Код ObjectModule — обработчики точек маршрута:**
   - `СогласоватьПередВыполнением()` — цепочка обработки завершения задачи
   - `УсловиеОбходЗавершен()` → `ОбходСогласующихЗавершен()`
   - `ОбработкаРезультатаОбработка()` → `ИтоговыйРезультатСогласования()` → `РаботаСБизнесПроцессами.ЗаписатьПроцесс`

5. **Алгоритм приоритетов `ИтоговыйРезультатСогласования()`** — найден полный приоритет: НеСогласовано > СогласованоСЗамечаниями > Согласовано, с кодом обхода строк ТЧ РезультатыСогласования

6. **Функция `ОбходСогласующихЗавершен()`** — SQL-запрос к `Задача.ЗадачаИсполнителя ГДЕ Выполнена = ЛОЖЬ`

7. **Общий модуль РаботаСВизамиСогласования** — процедуры `СоздатьВизыПоДействию`, `ОбновитьВизуУчастника`, `ПолучитьАктивныеВизыДокумента`; условие создания визы: `ДействияСогласования.ФормируетВизы = Истина`

8. **ManagerModule** — `ПроцессЗавершилсяУдачно()` с полным кодом, маппинг на `ВариантыВыполненияПроцессовИЗадач`

## Что сервер НЕ дал

1. **Значения перечисления РезультатыСогласования через metadatasearch** — вызов #4 вернул нерелевантный результат (только "РежимСокращенияТипа: ПреобразовыватьЗначения"). Значения пришлось получать через codesearch

2. **Полный перечень реквизитов ТЧ Исполнители** — реквизиты ВариантУстановкиСрокаИсполнения и ПорядокСогласования найдены, но полный список (Исполнитель, Пройден, Описание, ИдентификаторИсполнителя, ТрудозатратыПлан) не был выведен в одном чанке

3. **Полный текст `ОбработатьЗавершениеЗадачиСогласования()`** — только сигнатура вызова, без тела функции

4. **Точные значения ВариантыУстановкиСрокаИсполнения** — не перечислены

## Паттерны поведения агента

- **Сбалансированная стратегия**: агент чередовал metadatasearch (структура) и codesearch (код), получая комплементарные данные. 6 вызовов metadatasearch + 5 codesearch + 1 helpsearch
- **Высокая эффективность**: 83% полезных вызовов — лучший показатель из трёх серверов
- **Единственный retry** (#4→#5): metadatasearch не нашёл значения перечисления → codesearch нашёл их в коде. Грамотное переключение стратегии
- **Равномерное распределение токенов**: каждый вызов возвращал 5–14K символов, без экстремальных выбросов. Самый стабильный профиль расхода
- **Медленнее остальных**: ~6.5 минут против 2–4 минут у других серверов

## Вывод

**code-metadata** показал **лучший баланс** среди трёх серверов: работающий metadatasearch даёт структуру метаданных, codesearch — код логики. Это единственный сервер, где **оба инструмента** (metadatasearch + codesearch) функционируют стабильно. Высший процент полезных вызовов (83%), единственный retry. Слабость: неспособность metadatasearch вернуть значения перечислений и чуть большее время работы. Подходит для комплексных вопросов, требующих и структуры, и кода.
