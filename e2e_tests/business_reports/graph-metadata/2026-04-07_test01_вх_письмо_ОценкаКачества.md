**Оценщик:** Оркестратор (Claude Opus 4.6)

## Общая оценка: ЧАСТИЧНО (ближе к ПОЛНОСТЬЮ)

## Что сервер дал хорошо

1. **Полный список реквизитов** — execute_metadata_cypher по связи HAS_ATTRIBUTE вернул 80+ реквизитов ДокументыПредприятия. Это лучший результат среди трёх серверов — прямое перечисление без шума.
2. **Все 10 бизнес-процессов** с полными наборами реквизитов (Рассмотрение, Исполнение, Согласование, Регистрация и др.) — через Cypher по категории.
3. **46 состояний документа** — полное перечисление СостоянияДокументов через EnumValue. Ни один другой сервер не дал полный список.
4. **229 подписок на события** — полный список с идентификацией ~18 релевантных для ДокументыПредприятия. Агент разделил на ПередЗаписью (14 шт.) и ПриЗаписи (10 шт.) — самый детальный результат.
5. **Инфраструктура нумерации** — Нумераторы, НастройкиНумерации (11 измерений, 2 ресурса), ИндексыНумерации. Полная картина.
6. **Табличные части** — 11 шт., включая тст-расширения.
7. **Архитектура объекта** — правильно определил ДокументыПредприятия как Справочник, нашёл ВидыКорреспонденции (Входящая/Исходящая).

## Что сервер НЕ дал

1. **Код модуля объекта** — search_code провалился (5 попыток, 1 полезная). Fulltext-индекс не покрывает модуль ДокументыПредприятия.
2. **answer_metadata_question** — 2 вызова, оба бесполезны (уверенность 50%, общие ответы без фактов из индекса). LLM-инструмент неэффективен.
3. **business_search** — ошибка "Vector indexer not initialized". Инструмент полностью недоступен.
4. **Вызов #5 — катастрофа**: запрос `properties(n)` для ДокументыПредприятия вернул **1.6 МБ** текста с полным program_code всех форм. Агент сохранил в файл, но это потенциальная бомба для контекста.

## Паттерны поведения агента

- **30 вызовов** — больше всех (cloud-embeddings: 13, code-metadata: 18). Причина: агент активно использовал execute_metadata_cypher для навигации по графу — это требует много мелких запросов (узнать структуру → найти категорию → получить объекты → получить реквизиты).
- **execute_metadata_cypher = основной инструмент** (20 из 30 вызовов, 85% полезных). Агент быстро понял, что прямые Cypher-запросы — единственный надёжный способ.
- **search_metadata**: 3 вызова, 1 полезный. Слабый инструмент — плохой fulltext.
- **search_code**: 5 вызовов, 1 полезный. Индекс кода беден.
- **Умная стратегия**: агент запрашивал категории → объекты → реквизиты пошагово, а не пытался угадать одним запросом.

## Выявленные проблемы RAG

| Проблема                              | Проявление в этом тесте                                                                       |
| ------------------------------------- | --------------------------------------------------------------------------------------------- |
| properties(n) возвращает program_code | Вызов #5: 1.6 МБ за один запрос. Нужно НИКОГДА не запрашивать properties() для MetadataObject |
| search_code слабый fulltext           | 5 попыток, 1 полезная. Индекс не покрывает основные модули                                    |
| answer_metadata_question бесполезен   | LLM с уверенностью 50% генерирует общие ответы, не используя данные графа                     |
| business_search не работает           | "Vector indexer not initialized" — embedding для бизнес-описаний не создан                    |
| Граф = дерево                         | Нет связей документ→регистр, документ→БП. Агент находил их только по именам через WHERE       |

## Вывод

Graph-metadata — лучший сервер для **структурных/справочных вопросов**: полный список реквизитов, бизнес-процессов, состояний, подписок. Execute_metadata_cypher — мощный инструмент для тех, кто знает Cypher. Слабые места: поиск по коду (search_code), LLM-инструменты (answer_metadata_question, business_search), и опасность запроса properties() на узлах с program_code. Для бизнес-вопроса дал ~80% информации — больше всех по объёму фактов, но без кода.
