## Что сервер дал хорошо

- **Точная структура реквизитов** — execute_metadata_cypher вернул все 9 реквизитов шапки с типами в одном компактном запросе (#3, 683 символа)
- **Обе табличные части** — 16 реквизитов из ДополнительныеРеквизиты и КонтактнаяИнформация (#5, 1728 символов)
- **Полная карта связей**:
  - ФизическиеЛица → Сотрудники через РС.ОсновныеСотрудники (обнаружено через #16: ФизическоеЛицо(изм.) → Сотрудник(рес.))
  - Должности — прямой реквизит
  - СтруктураПредприятия — двусторонняя связь (Подразделение → Сотрудники; Руководитель → Сотрудники|Пользователи)
- **Механизм замещения** — полная структура ЗамещающиеИПомощники (#11), перечисление ВидыЗамещения (#12), формы (#33)
- **Исчерпывающий список регистров**:
  - 13 регистров сведений — полный список через Cypher-запрос по имени (#27)
  - 2 регистра накопления (РабочееВремяСотрудников, КоличествоДействийЗадач) с полной структурой
  - Детальная структура каждого ключевого регистра: ОсновныеСотрудники, СотрудникиПользователей, ПолномочияСотрудников, ЗанятостьСотрудников, ДоступноеВремяСотрудников, ХронометражРабочегоВремени, ПротоколРаботыСотрудников, НастройкиРабочегоКалендаря
- **Уникальные находки**: регистры ДанныеSAPСотрудники (интеграция SAP), ДокументыКВыгрузкеКабинетСотрудника, СотрудникиДляКонтроляСамочувствия — не найдены другими серверами
- **search_code** (#32) — подтвердил код работы с формой замещения

## Что сервер НЕ дал

- **search_metadata нерабочий** — требует OPENAI_API_KEY, которого нет. Вызов #1 вернул ошибку (354 символа). Но это компенсировано Cypher-запросами.
- **answer_metadata_question слабый** — вызов #26 («Как связан Сотрудники с ФизЛица?») получил 50% уверенности и общие слова без конкретных метаданных. LLM-инструмент не добавил ценности.
- **Стандартные реквизиты** (Код, Наименование, ПометкаУдаления) — в графе не хранятся. Это архитектурное ограничение: Neo4j содержит только пользовательские реквизиты.
- **Связь Сотрудники→ФизическиеЛица через Владелец** — в графе не видна подчинённость справочника (нет свойства ВладелецТипы). Агент не смог определить, что Сотрудники подчинён ФизЛицам — нашёл связь только через регистр ОсновныеСотрудники.
- **Обязательность полей и индексирование** — граф не хранит атрибуты ПроверкаЗаполнения и Индексирование.

## Паттерны поведения агента

- **Фаза 0**: попытка search_metadata → ошибка API → переключение на get_metadata_prompt для получения схемы графа
- **Фаза 1** (точечные Cypher): реквизиты шапки → узлы → ТЧ → ФизЛица → обратные связи → замещение → регистры
- **Фаза 2** (глубокое исследование): детальная структура каждого найденного регистра (по одному Cypher на регистр)
- **Ошибка properties(o)** (#7, 481K символов) — запросил ВСЕ свойства узла, получил весь граф. Быстро скорректировал (#8).
- **Синтаксическая ошибка Cypher** (#15) — переменная path не определена. Исправлено в #16.
- Агент выработал устойчивый паттерн: сначала широкий запрос (MATCH по типу связи), затем точечные запросы структуры каждого найденного объекта
- **35 вызовов** — максимум из трёх серверов, но каждый ответ компактный (100-3500 символов, исключая аварийный #7)

## Выявленные проблемы RAG
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| search_metadata требует OpenAI API | Полностью нерабочий без OPENAI_API_KEY. Критическая зависимость от внешнего сервиса. |
| answer_metadata_question низкое качество | 50% уверенности, общие слова. LLM-инференс на графе не работает для конкретных вопросов. |
| Нет стандартных реквизитов в графе | Код, Наименование, ВладелецТипы, ПометкаУдаления не хранятся. Нужны для полной картины. |
| Риск properties(o) | Запрос properties() на узле может вернуть весь граф (~481K символов). Нет защиты от таких запросов. |
| Нет атрибутов метаданных | ПроверкаЗаполнения, Индексирование, ДлинаНаименования — не хранятся в узлах графа. |

## Вывод

Сервер graph-metadata — **самый токен-эффективный** из трёх: получил полную структуру справочника (реквизиты, ТЧ, связи, 15+ регистров) за ~35K символов (без аварийного #7) против ~209K у code-metadata и ~196K у cloud. execute_metadata_cypher — мощнейший инструмент для навигации по структуре конфигурации, позволяющий точечно запрашивать именно нужные данные. Слабые стороны: нет стандартных реквизитов, нет атрибутов проверки/индексирования, search_metadata и answer_metadata_question неработоспособны. Сервер идеален для задач «найти все связанные объекты» и «показать структуру регистра», но требует навыков Cypher.
