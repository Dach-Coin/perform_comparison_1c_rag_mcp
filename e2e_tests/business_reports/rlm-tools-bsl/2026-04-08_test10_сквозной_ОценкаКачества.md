## Что сервер дал хорошо

1. **Полная цепочка объектов** — точно восстановлена последовательность: ВходящееПисьмо → БП.Рассмотрение → Справочник.Резолюции → БП.Исполнение → ЗадачаИсполнителя → ИсходящееПисьмо. Каждый переход подтверждён кодом
2. **Код процедур-переходов** — прочитаны ключевые процедуры:
   - РассмотретьПередСозданиемЗадач (создание задачи с резолюцией)
   - СформироватьИсполнениеОбработка (запуск БП Исполнение из Рассмотрения)
   - ЗаполнитьПоРассмотрению (копирование данных между БП)
   - ИсполнитьПередСозданиемЗадач (создание задач исполнителям с маршрутизацией)
   - ВыполнитьДействиеЗадачи (состояния задачи)
3. **Реквизит-связка ПисьмоОснование** — обнаружена прямая связь ИсходящееПисьмо.ПисьмоОснование → DocumentRef.ВходящееПисьмо, замыкающая сценарий
4. **Реквизит Предмет в ЗадачаИсполнителя** — включает DocumentRef.ВходящееПисьмо — прямая связь задачи с источником
5. **Процедуры ObjectModule обоих писем** — ПередЗаписью/ПриЗаписи с точными обращениями к регистрам
6. **Подписки на события** — 15 подписок для ВходящегоПисьма, 88 для ИсходящегоПисьма, 14 для ЗадачаИсполнителя
7. **9 регистров сведений + 3 регистра накопления** — задействованных в сценарии, с указанием шага
8. **Кастом Тест** — найден тст_ОбщегоНазначенияСервер.ОтправитьПисьмо для внешней отправки
9. **Резолюция = Справочник, не Документ** — неочевидный факт, который агент корректно выявил

## Что сервер НЕ дал

1. **Механизм прикрепления файлов** — подписки РаботаСФайлами обнаружены, но код прикрепления файла-ответа не прочитан (агент корректно отметил это как "не исследовалось глубоко")
2. **find_register_movements не работает для писем** — письма не проводятся, метод вернул пустоту (#24, #33). Агент обошёл через safe_grep
3. **Детали выбора Рассмотрение vs Согласование** — бизнес-логика маршрутизации на верхнем уровне не исследовалась (вне скоупа теста)

## Паттерны поведения агента

- **38 вызовов** — самый объёмный тест, оправданно: сквозной сценарий покрывает 5 шагов, 6 объектов метаданных, множество модулей
- **Быстрое восстановление**: analyze_document_flow (#3) вернул пустоту — агент немедленно переключился на find_module + find_event_subscriptions и пошёл "ручным" маршрутом
- **Обход ограничений**: find_register_movements не работает для непроводимых документов — агент заменил на safe_grep по тексту "РегистрыСведений" в модулях. Результат: нашёл все 9 РС + 3 РН
- **Mermaid-диаграмма**: агент самостоятельно построил flowchart всего сценария — наглядная визуализация для бизнес-отчёта
- **Покрытие кастома**: агент проверил тст_-модули на причастность к сценарию — нашёл отправку писем через тст_ОбщегоНазначенияСервер

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| analyze_document_flow пустой | Хелпер не вернул данных для ВходящегоПисьма (#3) — пришлось обходить вручную |
| find_register_movements не для всех объектов | Не работает для непроводимых документов (письма) — нужна документация или fallback |
| find_register_writers пустой | Метод (#33) не вернул данных — дублирует проблему с find_register_movements |

## Вывод

rlm-tools-bsl уверенно справился с самым сложным тестом — сквозным сценарием через 6 объектов метаданных. Ключевое преимущество: возможность прочитать код процедур-переходов между шагами (СформироватьИсполнениеОбработка, ЗаполнитьПоРассмотрению и т.д.) — это даёт не схему "как должно быть", а точное "как реализовано". Три шумных вызова (#3, #24, #33) связаны с хелперами, которые не работают для определённых типов объектов — агент быстро находил обходные пути через safe_grep.
