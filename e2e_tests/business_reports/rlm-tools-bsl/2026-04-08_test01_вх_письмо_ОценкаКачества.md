# Оценка качества: TEST-01 — Жизненный цикл входящего документа
**Сервер:** rlm-tools-bsl
**Дата:** 2026-04-08
**Оценщик:** Оркестратор (Claude Opus 4.6)

## Общая оценка: ПОЛНОСТЬЮ

| Метрика                | Значение     |
| ---------------------- | ------------ |
| Вызовов MCP            | 25           |

## Что сервер дал хорошо

1. **Полная структура объекта** — 23 реквизита и 4 табличные части ВходящегоПисьма через `parse_object_xml`, точные типы данных
2. **Код обработчиков** — полный текст `ПередЗаписью` (47 строк) и `ПриЗаписи` (58 строк) через `read_procedure`, включая логику работы с папками, проверку обязательности, рабочие группы
3. **Подписки на события** — 80+ подписок через `find_event_subscriptions`, с указанием модулей-обработчиков и событий (BeforeWrite ~18, OnWrite ~14, BeforeDelete ~4)
4. **Бизнес-процессы** — найдены все 10 БП конфигурации, подтверждена связь ВходящегоПисьма с БП Рассмотрение через прямую цитату кода: `ТипыПредметов.Добавить(Тип("ДокументСсылка.ВходящееПисьмо"))`
5. **Алгоритм заполнения** — полная логика `ЗаполнитьВходящееПисьмоИзСтруктурыПочтовогоСообщения` (реквизиты, получатели, вложения)
6. **Регистры** — выявлены 2 прямых регистра из ObjectModule + 14 регистров почтового модуля + 3 через подписки
7. **Нумерация** — механизм через подписку `OnSetNewNumber` → `ПрефиксацияОбъектовСобытия`
8. **Роли** — `РаботаСоВстроеннойЭлектроннойПочтой` с полным набором прав

## Что сервер НЕ дал

1. **Инициация БП из формы** — логика запуска бизнес-процесса по письму находится в ФормеДокумента, которую агент не исследовал до конца (осталась за рамками анализа)
2. **Регистр НастройкиОбработкиПисем** — упомянут в контексте правил, но не раскрыт полностью
3. **КОДСобытия** — объект не содержит BSL-модуля (только XML), что привело к 2 неудачным попыткам (#15, #16)

**Причины пропусков:** не ограничения сервера, а особенности конфигурации (КОДСобытия без BSL) и тайм-менеджмент агента (форма документа — обширный анализ). Сервер способен дать всё перечисленное при дополнительных вызовах.

## Паттерны поведения агента

- **Стратегия "от общего к частному"**: `search_objects` → `find_by_type` → `parse_object_xml` → `read_procedure` — эффективная воронка
- **Активное использование хелперов**: `find_event_subscriptions`, `extract_procedures`, `find_exports` — специализированные BSL-функции дают точные результаты
- **Быстрое восстановление после ошибок**: retry #6→7 (регистры через grep вместо movements) и #15→16→17 (find_module вместо прямого чтения) — агент адаптировался за 1-2 попытки
- **Батчинг**: несколько операций в одном `rlm_execute` (напр., call #7 — grep + find_by_type + extract_procedures)

## Выявленные проблемы RAG
| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| Нет проблем RAG | rlm-tools-bsl — не RAG-сервер, а инструмент прямого доступа к коду. Чанкинг, эмбеддинги и потеря контекста не применимы |
| Объект без BSL-модуля | КОДСобытия имеет только XML, нет BSL — агент потратил 2 вызова на обнаружение этого факта. Индекс мог бы содержать метаданные о наличии/отсутствии модулей |
| Нет трассировки форм | Формы документов не анализировались — нет быстрого способа получить "какие БП запускаются из формы" без чтения всего модуля формы |

## Вывод

rlm-tools-bsl показал **отличный результат** на задаче анализа жизненного цикла документа. Принципиальное отличие от RAG-серверов — прямой доступ к коду и метаданным даёт **точные ответы без галлюцинаций**. Все найденные факты подтверждены цитатами кода. Сервер оптимален для задач, требующих: структуры объектов, чтения процедур, поиска подписок на события, анализа регистров. Слабее для задач "какие БП можно запустить из UI" — это требует анализа форм.
