## Что сервер дал хорошо

1. **Полные метаданные объекта** — `parse_object_xml` вернул все 23 реквизита и 4 ТЧ ВходящегоПисьма в одном вызове. Аналогичные данные для трёх БП (Рассмотрение 59 рекв., Исполнение 30, Согласование 31) получены за один вызов.

2. **Полный код обработчиков** — `read_procedure` выдал исходный текст ПередЗаписью (42 строки) и ПриЗаписи (58 строк) с полной бизнес-логикой: валидация папки, применение правил почты, обновление КоличествоПисемВПапках, автозаполнение рабочих групп.

3. **Подписки на события** — `find_event_subscriptions` нашёл 87 подписок и классифицировал их (BeforeWrite 33, OnWrite 20+, BeforeDelete 7).

4. **Алгоритм создания письма** — через `safe_grep` + `read_file` найден полный код `ЗаписатьВходящееПисьмо` (транзакция, проверка дублей, заполнение реквизитов, запись текстов, регистрация бизнес-события) — 120+ строк BSL-кода.

5. **Регистры подсистемы почты** — grep по модулю `ВстроеннаяПочтаСервер` обнаружил 28 регистров сведений. Структуры 6 ключевых регистров получены через `parse_object_xml`.

6. **Нумерация** — раскрыт механизм: подписка `OnSetNewNumber` → `ПрефиксацияОбъектовСобытия.УстановитьПрефиксИнформационнойБазы`.

7. **Регламентные задания** — найдены 17 заданий подсистемы почты с флагами активности.

8. **Кастомизация Тест** — `find_custom_modifications` подтвердил 0 кастомных изменений.

## Что сервер НЕ дал

1. **Структура табличных частей** — `parse_object_xml` не возвращает колонки ТЧ (только имена секций). Для получения колонок нужен отдельный вызов `find_attributes` или парсинг XML вручную.

2. **Детали всех 87 подписок** — получены имена и обработчики, но не тела обработчиков. При 87 подписках анализ каждой потребовал бы ~87 дополнительных вызовов.

3. **Регистры накопления** — документ не проводится (0 движений), это корректный ответ, но агент потратил 2 вызова (#8, #9) на попытку найти writers.

## Паттерны поведения агента

- **Стратегия "от объекта к связям"**: начал с `find_module` → `parse_object_xml` → `extract_procedures` → `read_procedure` → затем расширил на БП, регистры, подписки. Это оптимальный паттерн для rlm-tools-bsl.
- **Ошибки обучения**: 3 retry — агент учился API инструментов (parse_object_xml принимает директорию, не файл; КОДСобытия — не CommonModule; read_procedure не нашёл экспортную функцию по имени). Все ошибки исправлены в следующем вызове.
- **Батчинг**: хороший — агент группировал связанные операции (parse_object_xml трёх БП за один вызов, grep + read в одном вызове).
- **Глубина исследования**: агент добрался до кода `ЗаполнитьВходящееПисьмоИзСтруктурыПочтовогоСообщения` (line 13072 в модуле 14000+ строк) — это глубокий drill-down.

## Выявленные проблемы RAG

| Проблема | Проявление в этом тесте |
| -------- | ----------------------- |
| parse_object_xml не возвращает колонки ТЧ | Агент получил 4 имени ТЧ, но 0 колонок — неполные метаданные |
| read_procedure не находит по частичному имени | #22: пустой результат для ЗаписатьВходящееПисьмо, хотя функция существует |
| Ошибка при передаче .mdo файла в parse_object_xml | #3: API принимает директорию, не файл — нужна лучшая документация |
| find_register_writers = 0 для всех регистров | #8: writers не в индексе, нужен grep по конкретному модулю |

## Вывод

rlm-tools-bsl показал **отличный результат** для комплексного вопроса о жизненном цикле документа. Сервер дал полную структуру объекта, исходный код обработчиков, подписки, регистры, механизм нумерации и код создания письма. Главное преимущество — доступ к реальному BSL-коду (read_procedure, safe_grep, read_file), что недоступно RAG-серверам. Проблемы минимальны: 3 retry из-за изучения API, быстро исправлены.
